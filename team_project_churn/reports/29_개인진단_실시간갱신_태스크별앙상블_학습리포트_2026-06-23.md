- 관련: 19-7-1(대시보드 IO계약), 17-2(초단위 세션이탈), 26-6(개인진단 3방식), [[BUG-005_얼굴로그인_흐름점검]](거버넌스: 임의 학습본 무단투입 금지)

## 0. 요청 요약(사용자)

1. **실시간 갱신**: 진단 카드가 정적 → 자동 새로고침(몇 초 뒤 갱신·예측 작업현황 표시).
2. **속도 개선**("왜 이렇게 느려?"): 다회 호출 → 단일 통합 엔드포인트로 라운드트립 축소.
3. **내부 앙상블 현황**: 어떤 모델이 몇 %로 예측하는지 + 앙상블 합산 %.
4. **churn 3종 세분화**: ① 기존 모델 7일 이탈확률 ② 하자드 적용확률 ③ 바운스 확률(+기준시간).
5. **태스크별 앙상블 원칙**: "모델7은 churn끼리, 바운스는 바운스끼리." → **카테고리 추천 4종 / 바운스 6종**(기존 LogReg 포함) 목표로 boost3+Transformer 추가 학습.
6. **자원 제약**: CPU 코어 일부 남기고 가용율 여유 유지하며 학습.
7. 결과를 **발표용 리포트**로 제출.

진행 순서(사용자 지시): **① 당장 가능한 프레임워크+현존 모델 먼저 → ③ 없는 모델 학습해 합류**.

## 1. Phase 1 — 실시간 갱신 · 통합 진단 · 내부 앙상블 현황 (완료)

### 1.1 백엔드 통합 엔드포인트 `GET /predict/diagnose?user_id=`
- 신규 `application/diagnose_usecase.py` + `interfaces/http/predictions_router.py` 라우트.
- **태스크별 앙상블 원칙** 준수: churn 태스크는 churn 모델끼리.
- 한 번의 호출로 다음을 반환(기존 다회 호출 대비 라운드트립 ↓ → 체감 속도 개선):
  - `churn.models`: **모델별 이탈확률**(CatBoost·XGBoost·LightGBM 각각) — "어떤 모델이 몇 %"
  - `churn.ensemble_prob`: **앙상블 합산 %**(domain.ensemble 가중평균) + `improvement`(편차 진단)
  - `hazard`: recency_days 기반 Weibull 생존 hazard(τ=7d, k=1.3) — "하자드 적용확률"
  - `recency_days`: 마지막 활동 후 경과일(n일 만의 방문 표시용)
- 실측 예시(user 613590885): CatBoost 100.0% / XGBoost 63.4% / LightGBM 47.9% → **앙상블 70.4%(고위험)**, 하자드 63.2%.

### 1.2 대시보드 자동 갱신 `dashboard_streamlit/pages/02_dashboard.py`
- `@st.fragment(run_every=5)` `live_diagnosis()` — **5초마다 자동 재추론**, "🔄 5초마다 자동 갱신 · 마지막 갱신 HH:MM:SS" 상태 표시.
- **churn 3종 메트릭**(st.columns 3): ① 7일 이탈(앙상블) ② 하자드(recency) ③ 세션/바운스(시뮬 라이브).
- **내부 앙상블 현황 표**: 모델별 % → ▶ 앙상블(가중평균) %, + 편차 개선 코멘트.
- 행동이력 없는 ID(가입 ID)는 해시 기반 **대표 고객(shadow) 고정 매핑**으로 대체 표시(26-6 정합).

### 1.3 시뮬 사이트 3종(팀 동시작업, 정합 확인)
- `sim_external_router /api/churn/predict` → `churn_breakdown`[7일·하자드·bounce(30분)] 반환, `FloatingChurnWidget.tsx`가 3종 바 렌더(4초 폴링). 대시보드(개인 진단)와 시뮬(라이브 세션)이 각각 3종을 표시.

## 2. Phase 2 — 보조 태스크 앙상블 학습 (완료)

### 2.1 방법
- 입력은 **시퀀스 npz**(X_cat (N,10), X_num (N,10,6)). 부스팅은 시퀀스를 직접 못 먹으므로 **flatten+집계로 탭ular 81피처**(60 flatten + mean/max/last 18 + 시퀀스길이·고유카테고리수·마지막카테고리 3) 생성.
- Transformer는 시퀀스 그대로 사용(임베딩+수치투영+positional, mean-pool, 2-layer encoder).
- **자원 제약 준수**: BLAS/OMP 스레드 = 3, 부스터 n_jobs/thread_count=3, `torch.set_num_threads(3)` (8코어 중 5코어 여유 ≈ 60%+). 모델별 try/except로 부분 실패 격리.
- 스크립트: `scripts/train_aux_ensembles.py`(학습), `scripts/evaluate_aux_ensembles.py`(동일 테스트셋 모델별+앙상블 평가), `scripts/fix_category_boosters.py`(다중분류 부스터 보강 시도).

### 2.2 세션 바운스(이진, churn=세션이탈) — **5종 동일타깃 앙상블**
테스트 n=179,163 · 지표 ROC-AUC

| 모델 | AUC | PR-AUC | F1 | 비고 |
|---|---|---|---|---|
| GRU(기존, 모델팀) | 0.8297 | 0.6013 | 0.548 | 시퀀스 |
| LightGBM(신규) | 0.8311 | 0.6064 | 0.550 | 탭ular |
| XGBoost(신규) | 0.8307 | 0.6047 | 0.551 | 탭ular |
| CatBoost(신규) | 0.8294 | 0.6012 | 0.552 | 탭ular |
| Transformer(신규) | 0.8250 | 0.5817 | 0.560 | 시퀀스 |
| **▶ 앙상블(5종, soft-vote)** | **0.8315** | **0.6061** | 0.554 | **모든 단일모델 ≥** |

- **앙상블 AUC 0.8315 = 최고 단일모델 이상** → 앙상블 효과 입증.
- 기존 **LogReg는 event-level churn30(다른 타깃·다른 피처셋)** 이라 동일 블렌딩에서 제외(별도 6번째 자료로 보유). "바운스는 바운스끼리" 원칙상 **동일 타깃 5종**이 정합. (LogReg까지 자료 6종 보유)

### 2.3 카테고리 추천(다중분류, 471/516 vocab) — **가중 앙상블**
테스트 n=100,000 · 지표 top-1/top-5

| 모델 | top-1 | top-5 | 비고 |
|---|---|---|---|
| GRU(기존, 모델팀) | 0.6241 | 0.7830 | 시퀀스 |
| Transformer(신규) | 0.6188 | 0.7761 | 시퀀스 |
| LightGBM(신규) | 0.1792 | 0.3601 | 탭ular(약함) |
| 앙상블(단순평균) | 0.5766 | 0.7721 | 약한 부스터가 끌어내림 |
| **▶ 앙상블(성능가중)** | **0.6243** | 0.7775 | **최고 단일모델 ≥** |

- **핵심 인사이트**: next-category는 **시퀀스 순서**가 본질 → 시퀀스 모델(GRU·Transformer)이 강하고, 시퀀스를 평탄화한 부스팅은 약함(top-1 0.18). 따라서 **단순평균은 오히려 성능 저하**, **성능비례 가중 앙상블**이 최고 단일모델을 회복·소폭 상회(가중 GRU 0.439·Transformer 0.435·LightGBM 0.126).

## 3. 한계 · 정직성(발표 Q&A 대비)

1. **카테고리 XGBoost/CatBoost(474클래스) 제외**: 다중분류 471클래스 학습이
   - XGBoost: train split이 전체 클래스를 안 담아 sklearn 래퍼 거부 → 저수준 API 재시도했으나 학습비용 과다(클래스당 트리)로 실효성 낮음.
   - CatBoost: MultiClass 471클래스가 RAM 초과(bad allocation).
   - → **LightGBM이 부스팅 대표**로 잔류. 부스팅이 이 태스크에 본질적으로 약하므로(2.3) 가치-비용상 합리적 선택. (자원·시간 확보 시 모델팀 정식 학습으로 보강 권장)
2. **탭ular 변환의 정보손실**: flatten+집계는 시퀀스 순서를 부분만 보존 → 부스팅 한계의 원인(특히 카테고리).
3. **데모 학습 수준**: 발표용 보조 산출물. 부스터 early-stopping·Transformer 4 epoch. 최종 운영 모델은 모델팀 정식 학습(전체 데이터·하이퍼튜닝) 권장.
4. **거버넌스**([[BUG-005_얼굴로그인_흐름점검]]): bounce 모델은 임의 실험물이 아니라 **model_3 브런치 정식 산출물(GRU)** 기반, 추가 학습본은 동일 데이터·동일 split으로 재현 가능하게 산출.

## 4-b. 후속 수정 (사용자 피드백 4건, 2026-06-23)

1. **"값이 안 변함"** — 정상 동작. ①7일앙상블·②하자드는 **저장된 과거 v2 피처**로 계산되는 결정적 값이라 이력이 바뀌지 않으면 불변. 실시간으로 변하는 건 **③(시뮬 세션)** 뿐. → 메트릭 라벨을 `① 7일(과거 앙상블)`·`② 하자드(과거 recency)`로 명시하고 "정적" 안내 캡션 추가.
2. **"왜 5초?"** — 근거 없는 임의값이었음. → **갱신주기 선택(2/5/10/30초)** UI 추가(`st.fragment(run_every=)` 동적 주입). 과거 ①②는 정적이라 주기 무관, 시뮬 ③만 주기마다 갱신됨을 명시.
3. **시뮬 Cart 옆 접속 유저 ID** — `POST/GET /sim/active-user`(+raw `/api/active-user`) + `sim_usecase.set_active_user/get_active_user`. 대시보드에서 유저 선택 시 서버에 설정 → 시뮬 `ProductList.tsx` 헤더가 5초 폴링해 `User: <id>` 배지 표시(서버 동기화, 없으면 로컬 세션 userId).
4. **대시보드↔시뮬 3종 차이** — 원인: 대시보드 ①②는 **과거 이력 기준**, 시뮬은 **실시간 세션 기준**(입력 자체가 다름). → `churn_three`가 실시간 3종 전체를 `_LAST_SIM`에 캐시 → `/sim/user-score`가 동일 breakdown 반환. ③ 바운스는 시뮬 `churn_bounce`(30분 기준) 직접 사용 → 시뮬 사이트와 완전 일치(검증: 13.2%/2.0%/70.6% 동일).
5. **과거+실시간 동시 표시**(사용자 추가 요청) — 진단 카드를 **두 블록**으로 분리 표시:
   - **📊 과거 이력 기준(정적)**: ① 7일 이탈(앙상블) · ② 하자드(recency)
   - **⚡ 실시간 세션 기준(시뮬 동일)**: ① 7일(세션) · ② 하자드(세션) · ③ 바운스(30분). 시뮬 미활동 시 "시뮬 대기" 안내.
   - 상단 🎯 Churn Rate(액션 기준 = 3종 최댓값) + 하단 "과거 vs 실시간 차이 사유" 캡션.

## 5. 발표 포인트(3줄)
1. **개인 진단이 5초마다 살아 움직이며**, churn을 3종(7일 앙상블/하자드/세션바운스)으로 쪼개고 **어떤 모델이 몇 %인지 + 앙상블 합산 %**까지 투명하게 보여준다.
2. **태스크별 앙상블 원칙**대로 세션 바운스 5종을 합쳐 **AUC 0.8315(단일 최고 이상)** 달성 — 앙상블 이득 실증.
3. 카테고리 추천은 **시퀀스 모델이 본질**임을 데이터로 보이고(부스팅 0.18 vs 시퀀스 0.62), **성능가중 앙상블**로 최고 단일모델을 회복 — "무지성 평균이 답이 아니다"를 정량으로 제시.
