# 19-2. 최종 백엔드 설계도 - FastAPI/Python 반영본

기준 문서: [05-6-4](05-6-4_프로그램_구조도_및_함수_변수_비전_명세서.md), [19-0](19-0_백엔드_DB_MySQL_계획서.md), [19-1](19-1_최종_백엔드_설계도.md), [17-6-5](17-6-5_5m_models7_호환성정합_및_개선_계획서.md)

본 문서는 현재 확정된 **가지마 대시보드 운영 백엔드**의 FastAPI/Python 반영 설계도다. `19-0`은 MySQL/백엔드 계획 초안, `19-1`은 Node/Fastify 기준 설계도로 보존하고, 본 `19-2`를 Python ML 프로젝트와 연결되는 구현 기준으로 삼는다.

---

## 1. 최종 결정 요약

| 항목 | 최종 결정 |
| --- | --- |
| 백엔드 | Python FastAPI 서버, 클린아키텍처 계층 분리 |
| 운영 DB | MySQL 8 |
| 시뮬 로그 | Neon Postgres, 외부 이벤트 소스 |
| 대시보드 | `dashboard_streamlit/` |
| 시뮬 사이트 | `simulation_site/` |
| 전처리 정본 | `data/processed/` 단일 루트 |
| 운영 라벨 | `churn` 단일 |
| 예측 의미 | **향후 7일 이탈 확률** |
| 모델 학습 | 백엔드 밖 `src/`/모델파트 |
| 모델 평가 | 학습 파이프라인이 산출, 백엔드는 ingest/서빙 |
| 대용량 파일 | parquet/npz/model artifact는 DB 밖 파일, DB에는 경로 |

**핵심 원칙**
- 백엔드는 학습하지 않는다.
- 백엔드는 운영 API, 레지스트리, 평가 산출물 ingest, 예측 로그, 추천/리텐션, 대시보드용 chart-ready JSON을 책임진다.
- Neon은 운영 DB가 아니라 `simulation_site`의 외부 이벤트 저장소다.
- Streamlit은 DB에 직접 붙지 않고 백엔드 REST만 호출한다.

## 4. 백엔드 클린아키텍처 매핑

| 계층 | 폴더 | 책임 |
| --- | --- | --- |
| Interface | `interfaces/http/` | API 라우트, 요청/응답 검증, 로그인·권한 검사 |
| Schemas | `schemas/` | Pydantic 요청/응답 모델 |
| Application | `application/` | 모델 등록, 예측, 대시보드 조회 같은 업무 흐름 조립 |
| Domain | `domain/` | 위험등급, 모델 상태, 추천/리텐션 규칙 |
| Infrastructure | `infrastructure/mysql/` | MySQL repository |
| Infrastructure | `infrastructure/external_neon/` | Neon 시뮬 이벤트 외부 adapter |
| Infrastructure | `infrastructure/files/` | artifact path, parquet/json metadata reader |
| Infrastructure | `infrastructure/model_inference/` | 모델 예측 실행 adapter 또는 Python worker client |
| Validators | `validators/` | 스키마 외 추가 검증, 파일 경로/모델 manifest 검증 |

**의존 방향**

```text
HTTP routes -> application usecases -> domain rules
                                      -> repository/model_inference ports
                                      -> infrastructure adapters
```

라우터가 SQL을 직접 실행하지 않는다. usecase가 파일 경로를 직접 해석하지 않는다. artifact와 DB 접근은 infrastructure adapter로 제한한다.

### 6.1 핵심 테이블

| 테이블 | 목적 |
| --- | --- |
| `model_registry` | 모델 파일, 전처리 config, dataset path, active 상태 |
| `model_evaluation` | 모델 평가 요약, chart JSON, raw 평가 파일 경로 |
| `prediction_log` | 운영 예측 로그, 향후 7일 이탈 확률 |
| `feature_user_snapshot` | 예측 시점 유저 피처 스냅샷 |
| `sequence_snapshot` | 시퀀스 파일 경로와 row index |
| `user_interest` | 추천용 유저 관심 카테고리/브랜드 |
| `recommendation` | 추천 결과 |
| `retention_action_log` | 쿠폰/리마인드/추천 액션 |
| `ensemble_result` | 다모델 조합 결과 |
| `ensemble_member` | 앙상블 구성 모델별 확률/가중치 |
| `face_user` | 얼굴 로그인 사용자 식별, `role` 기본값은 `customer` |
| `face_login_log` | 얼굴 로그인 성공/실패 로그 |

### 6.2 FK 원칙

강제 FK:
- `prediction_log.model_id -> model_registry.model_id`
- `recommendation.model_id -> model_registry.model_id`
- `retention_action_log.prediction_id -> prediction_log.prediction_id`
- `ensemble_member.ensemble_id -> ensemble_result.ensemble_id`

논리참조:
- `face_user.user_id`는 여러 테이블의 `user_id` 기준이지만 강제 FK로 묶지 않는다.
- 이유: 시뮬 이벤트나 외부 로그가 face 등록 전 유저를 먼저 만들 수 있다.

### 6.3 model_evaluation 추가

`19-0`에는 약했던 모델 검증/차트 산출물 저장을 `19-1`에서 보강한다.

```sql
CREATE TABLE model_evaluation (
  eval_id BIGINT AUTO_INCREMENT PRIMARY KEY,
  model_id BIGINT NOT NULL,
  dataset_tag VARCHAR(64) NOT NULL,
  split_name VARCHAR(32) DEFAULT 'test',
  horizon_days INT DEFAULT 7,
  label_name VARCHAR(32) DEFAULT 'churn',
  n_samples BIGINT,
  positive_rate DOUBLE,
  roc_auc DOUBLE,
  pr_auc DOUBLE,
  best_threshold DOUBLE,
  best_f1 DOUBLE,
  confusion_json JSON,
  threshold_curve_json JSON,
  calibration_json JSON,
  lift_curve_json JSON,
  score_distribution_json JSON,
  training_history_json JSON,
  eval_predictions_path TEXT,
  shap_summary_path TEXT,
  business_value_path TEXT,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_eval_model FOREIGN KEY (model_id) REFERENCES model_registry(model_id)
);
```

큰 데이터(`eval_predictions.parquet`, SHAP raw, business simulation raw)는 파일로 둔다.

### 7.4 팀 간 I/O 계약 불변 원칙

`19-2`에서 바뀌는 것은 백엔드 내부 구현체와 폴더명이다. 모델팀·대시보드팀·시뮬레이션팀이 맞춰야 하는 외부 계약은 유지한다.

| 구분 | 유지되는 계약 | 바뀌는 부분 |
| --- | --- | --- |
| 모델팀 입력 | `data/processed/`의 정본 parquet/npz, `feature_schema_version`, `preprocessing_config` | 없음 |
| 모델팀 출력 | `model_run_manifest.json`, metric/curve/shap/business JSON, `eval_predictions.parquet`, 모델 artifact 경로 | 없음 |
| 모델 등록 | `POST /models/submit` payload 구조 | 백엔드 내부 처리 파일만 Python/FastAPI로 변경 |
| 운영 DB | `model_registry`, `model_evaluation`, `prediction_log` 중심 스키마 | 없음 |
| 대시보드 | `/dashboard/*`, `/models/:id/charts/*`, `/predictions/*` 응답 JSON | 서버 실행체만 FastAPI로 변경 |
| 시뮬 사이트 | Neon 이벤트 저장, backend pull 흐름 | 없음 |

따라서 다른 팀원이 해야 하는 작업은 그대로다.
- 모델팀은 기존처럼 학습 후 manifest와 평가 산출물을 내면 된다.
- 대시보드팀은 기존 REST endpoint와 응답 JSON만 바라보면 된다.
- 시뮬레이션팀은 Neon 이벤트 저장 구조를 유지하면 된다.
- 바뀌는 것은 백엔드 개발자가 `backend/app/` 안에서 FastAPI 계층으로 구현하는 방식이다.

## 9. 주요 Usecase 흐름

### 9.1 모델 등록

```text
POST /models/submit
-> validate manifest
-> artifact path 존재/형식 확인
-> model_registry upsert
-> model_evaluation insert
-> active=true면 동일 model_type 기존 active 해제
-> response { model_id, eval_id }
```

### 9.2 실시간 예측

```text
simulation_site 이벤트 발생
-> Neon sim_event_log 저장
-> backend pull worker
-> 현재 시점 기준 feature_user_snapshot 생성
-> active churn model 조회
-> preprocessing_config에 맞춰 transform
-> model_inference adapter 또는 model worker 호출
-> churn_probability 저장
-> risk_level 계산
-> prediction_log 저장
-> recommendation/retention 후보 생성
```

예측 의미:

```text
현재까지의 행동을 기준으로 향후 7일 동안 이벤트가 없을 확률
```

### 9.3 대시보드 그래프 제공

```text
dashboard_streamlit -> /models/:id/charts/calibration
backend -> model_evaluation.calibration_json 조회
backend -> 없으면 eval_predictions_path에서 사전 계산된 artifact 조회
backend -> chart-ready JSON 반환
```

백엔드가 모델 재학습을 하지 않는다. 차트 원천은 학습 종료 시점 산출물이다.

## 10. Model Inference 정책

백엔드의 원칙은 **학습 금지**다. 다만 운영 예측은 필요하므로 모델 예측 실행부는 `infrastructure/model_inference/`로 분리한다.

| 방식 | 사용 조건 |
| --- | --- |
| `python_model_loader.py` | FastAPI 프로세스 안에서 직접 로드 가능한 CatBoost/LightGBM/sklearn 모델 |
| `model_worker_client.py` | PyTorch/LSTM/Transformer처럼 무거운 모델을 별도 Python worker에서 실행 |
| `batch_prediction_importer.py` | 모델파트가 미리 낸 예측 결과를 등록하는 데모/배치 |

권장:
- 1차 구현: `batch_prediction_importer.py` + chart API
- 2차 구현: CatBoost/GBM용 `python_model_loader.py`
- 3차 구현: LSTM/Transformer용 `model_worker_client.py`

추천과 다음 카테고리는 churn 모델의 부산물이 아니라 별도 태스크다.

```text
data/processed/recommendation/
data/processed/next_category/
models/recommendation/
models/next_category/
```

다음 카테고리 모델군:
- Baseline: Popularity, Last-category
- Tabular/Ranking: GBM 또는 LightGBM Ranker
- Sequence: GRU, Transformer, SASRec

운영 리텐션 흐름:

```text
향후 7일 이탈확률 high
-> user_interest 조회
-> recommendation 생성
-> retention_action_log 기록
-> dashboard_streamlit 표시
-> 필요 시 simulation_site로 push
```

## 14. 완료 기준

- `dashboard_streamlit`이 MySQL/Neon에 직접 접속하지 않는다.
- 모델 등록은 `POST /models/submit` 하나로 가능하다.
- active model 기준으로 최신 예측과 대시보드가 조회된다.
- 향후 7일 이탈 확률이라는 문구가 화면/문서/API에서 일관된다.
- PR-AUC, calibration, lift, SHAP, revenue simulation 등 발표 그래프를 API로 제공할 수 있다.
- 대용량 parquet/npz/model 파일은 DB에 직접 저장하지 않고 경로만 저장한다.
