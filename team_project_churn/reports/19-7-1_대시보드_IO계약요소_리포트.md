## 1. 핵심 원칙

대시보드는 **DB, 모델 파일, parquet/json 산출물을 직접 읽지 않는다.** 모든 데이터는 FastAPI 백엔드 REST 응답으로 받는다. 백엔드가 아직 준비되지 않은 경우에만 같은 schema의 `dashboard_streamlit/mocks/` 파일을 사용한다.

| 구분 | 대시보드가 하는 일 | 대시보드가 하지 않는 일 |
| --- | --- | --- |
| 로그인 | 이미지 업로드, API 호출, session_state 저장 | 얼굴 임베딩 직접 계산 |
| 예측 | 최신 예측/고위험 목록 조회, 화면 표시 | 모델 직접 로드, churn 계산 |
| 추천 | 추천 JSON 조회, 추천 카드 렌더링 | 추천 알고리즘 직접 계산 |
| 리텐션 | 액션 실행 버튼, 액션 기록 API 호출 | DB 직접 insert |
| 시각화 | chart-ready JSON 렌더링 | parquet/raw metric 직접 집계 |
| mock | 실서버 전 schema와 화면 개발 | 운영 데이터 원천으로 사용 |

환경변수:

```text
DASHBOARD_API_BASE_URL=http://localhost:8090
```

## 3. 앱 시작 I/O 흐름

```text
1. app.py 실행
2. session_state 기본값 설정
3. GET /health
4. 로그인 상태 없으면 01_face_login.py 표시
5. 로그인 성공 시 user_id/display_name/role 저장
6. 02_dashboard.py 표시
7. GET /dashboard/summary
8. GET /models/active
9. GET /dashboard/user/:userId
10. GET /predictions/latest?user_id={userId}
11. GET /recommendations/:userId
12. GET /predictions/top-risk
13. 핵심8 chart API 호출
```

session_state 필수값:

| key | 기본값 | 설명 |
| --- | --- | --- |
| `is_logged_in` | `False` | 로그인 여부 |
| `user_id` | `None` | 현재 사용자 ID |
| `display_name` | `None` | 화면 표시 이름 |
| `role` | `customer` | 기본 role. 개발자/관리자 분리 화면 없음 |
| `active_model_id` | `None` | 모델별 chart 조회 기준 |

## 4. 로그인 I/O 계약

얼굴 로그인은 `multipart` 이미지 업로드 방식이다. 프론트는 이미지를 전송하고, 백엔드가 임베딩/매칭/저장을 담당한다.

| 순서 | Method | Endpoint | 프론트 입력 | 백엔드 출력/저장 |
| --- | --- | --- | --- | --- |
| ID 확인 | GET | `/auth/face/check-id?user_id={userId}` | `user_id` | `{user_id, exists, available}` |
| 얼굴 등록 | POST multipart | `/auth/face/register` | `user_id`, `display_name`, `image` | `face_user` 생성, role 기본 `customer` |
| 얼굴 로그인 | POST multipart | `/auth/face/login` | `user_id`, `image` | `face_login_log` 저장, 사용자 정보 반환 |
| 내 정보 | GET | `/auth/me` | API key/session | 현재 사용자 정보 |

로그인 성공 후 대시보드 저장값:

```python
st.session_state.is_logged_in = True
st.session_state.user_id = str(user["user_id"])
st.session_state.display_name = user.get("display_name", "고객")
st.session_state.role = user.get("role") or "customer"
```

## 7. Mock I/O 계약

mock은 백엔드 미완성 시 화면 개발용이다. 운영 모드에서는 사용하지 않는다.

| mock 파일 | 실제 endpoint |
| --- | --- |
| `mocks/dashboard_summary.json` | `/dashboard/summary` |
| `mocks/user_dashboard.json` | `/dashboard/user/:userId` |
| `mocks/latest_prediction.json` | `/predictions/latest?user_id={userId}` |
| `mocks/top_risk.json` | `/predictions/top-risk` |
| `mocks/recommendations.json` | `/recommendations/:userId` |
| `mocks/session_bounce.json` | `/session-bounce/latest?session_id={sessionId}` 후보 |
| `mocks/charts/system_architecture.json` | `/dashboard/charts/system-architecture` |
| `mocks/charts/cohort_retention.json` | `/dashboard/charts/cohort-retention` |
| `mocks/charts/baseline_comparison.json` | `/dashboard/charts/baseline-comparison` |
| `mocks/charts/pr_auc.json` | `/models/:modelId/charts/pr-auc` |
| `mocks/charts/threshold.json` | `/models/:modelId/charts/threshold` |
| `mocks/charts/lift.json` | `/models/:modelId/charts/lift` |
| `mocks/charts/calibration.json` | `/models/:modelId/charts/calibration` |
| `mocks/charts/revenue_recovery.json` | `/models/:modelId/charts/revenue-recovery` |

규칙:
- mock 파일명은 `chart-name`을 snake_case로 바꾼다. 예: `pr-auc` -> `pr_auc.json`.
- mock과 실제 API 응답 wrapper는 같아야 한다.
- mock에서 화면을 완성한 뒤 `DASHBOARD_USE_MOCK=false`로 전환한다.

## 8. 구현 순서

1. `services/api_client.py` 작성: GET/POST, API key header, timeout, mock read 공통 처리.
2. `services/auth_service.py` 작성: `check-id`, `register`, `login`, `me`.
3. `services/dashboard_service.py` 작성: summary, user dashboard.
4. `services/prediction_service.py` 작성: latest, top-risk, realtime, session-bounce 후보.
5. `services/recommendation_service.py` 작성: recommendations, retention action.
6. `services/chart_service.py` 작성: active models, model evaluation, 핵심8/15개 chart 호출.
7. `components/charts.py` 작성: chart wrapper를 받아 line/bar/heatmap/matrix 렌더링.
8. `pages/01_face_login.py` 작성: multipart 이미지 업로드.
9. `pages/02_dashboard.py` 작성: 통합 대시보드 탭 구성.
10. `mocks/` 작성 후 `DASHBOARD_USE_MOCK=true`로 화면 확인.
11. 백엔드 실행 후 `DASHBOARD_USE_MOCK=false`로 실제 API 확인.

## 10. 최종 결론

대시보드 I/O 계약은 아래처럼 정리한다.

1. 대시보드는 `dashboard_streamlit/` 단일 통합 화면으로 만든다.
2. 모든 데이터는 FastAPI REST로 받으며, 운영에서 DB/모델/산출물 파일을 직접 읽지 않는다.
3. 로그인은 multipart 이미지 업로드 기반이고, role 기본값은 `customer`다.
4. 핵심 시각화는 27번의 8개로 우선 노출한다.
5. SHAP은 선택/부록이며 feature importance 폴백을 둔다.
6. 추천은 top-k 카테고리와 top-k 상품을 함께 받을 수 있게 만든다.
7. 세션 바운스는 신규 I/O로 화면 자리를 먼저 만들고, 백엔드 endpoint 확정 전에는 mock으로 개발한다.
