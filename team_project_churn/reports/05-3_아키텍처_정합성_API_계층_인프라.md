# 05-3 아키텍처 정합성 — API / 클린아키텍처 수준 / 인프라

목적: 12 리포트의 "개념만" 지침과, **확정된 요구사항**(DB 중심 + Vercel API + Streamlit + 얼굴로그인, REES46 소스)을 **모순 없이 정합**시키는 결정 문서. 범위는 아래 **3개 축에 한정**한다.

> 전제 정정: DB·Vercel·Streamlit·얼굴로그인은 **팀 결정 요구사항**이다. 따라서 12 리포트의 메시지는 "짓지 마라"가 아니라 **"형식주의(풀 DDD)를 강제하지 마라"** 로 읽어야 하며, *요구가 정해진 지금은 "최소·올바르게 짓자"* 로 재정렬한다.

---

## 0. 12 리포트 ↔ 현재 결정 재해석

| 12의 원문 취지 | 오해 소지 | 결정에 맞춘 재해석 |
| --- | --- | --- |
| "FastAPI/클린아키텍처 *개념만*" | "API/DB 만들지 마라"로 읽힘 | API/DB는 **만든다**. 단 **얇고 단순하게**(형식주의 배제) |
| "L2면 충분, L3 과함" | 계층화 자체를 하지 말라? | 계층화는 **한다**. 단 **DDD/Protocol 같은 풀 L3는 생략** |
| "로컬 파일이면 충분" | DB 쓰지 마라? | **DB가 단일 진실원천**. 파일은 *모델 아티팩트·실험 캐시*로 한정 |

핵심: **12의 진짜 원칙(경계 합의·관심사 분리·누수 방지)은 그대로 유효**하다. 바뀌는 건 "인프라를 실제로 둔다"는 점뿐이다.

---

## 1. API (Vercel) — "얇게" 짓는다

**결정**: Vercel에 프로젝트를 올리고, **API가 DB와 통신**한다(Neon 등). → API는 만든다.

**적용 원칙 (Thin API)**
- API의 책임은 **전송 + DB I/O + 인증/검증** 뿐. **ML 추론 로직·전처리는 API 안에 넣지 않는다.**
- 엔드포인트는 **최소**로: `POST /api/events`, `GET /api/events/recent`, `POST /api/predictions`, `GET /api/predictions/latest`, `GET /api/dashboard/summary`, `POST /api/auth/login-log`.
- 무거운 추론은 (a) Colab/배치로 미리 계산해 `prediction_log`에 적재하거나, (b) 가벼운 모델만 서버리스에서 추론. **서버리스 함수에 큰 .pth 로딩은 콜드스타트/용량 문제** → 배치 적재 권장.
- 비밀(DB URL 등)은 **서버 환경변수**에만. 브라우저/Streamlit 노출 금지.

**클린아키텍처 관점**: API = "Interface Adapter" 한 겹. 도메인/Protocol 계층 **불필요**.

## 2. 클린아키텍처 수준 — "실용적 L2+"

**결정**: DB·서비스·API·프론트 다계층이 생긴다. 그렇다고 풀 DDD(L3) 갈 필요는 없다.

**적용 원칙 (폴더·함수 분리 = L2+)**
```
frontend_streamlit/services/   ← UI와 분리된 호출 계층(db_service, prediction_service, face_auth)
src/ (ingest/build_features/train/predict)  ← 학습·전처리 (순수 로직)
db/db_client.py                ← DB 입출력 한 곳
vercel_api/api/*               ← 전송 계층
```
- **하지 않을 것**: `domain/entity`, `Protocol` 인터페이스, DI 컨테이너 같은 형식주의(L3).
- **할 것**: ① 파일=단일책임 ② **경계 산출물 합의**(feature/sequence 스키마·모델 인터페이스·API 응답 포맷) ③ UI↔서비스↔DB **호출 방향 한 방향** 유지.
- 효과: 나중에 Streamlit→Next.js, 직접DB→API로 바꿔도 **호출 계층만 교체**.

## 3. 인프라 — "DB가 단일 진실원천, 파일은 보조"

**결정**: 모든 데이터가 DB(예: Neon Postgres)를 통한다. CSV/NPZ는 보조.

**적용 원칙 (경계 명확화)**
| 데이터 | 저장 위치 | 비고 |
| --- | --- | --- |
| 원본/실시간 이벤트, 라벨, 예측, 로그인 | **DB 테이블** | 팀 공유 기준 = DB |
| **모델 파일**(.pth/.joblib/scaler) | **파일시스템(`models/`)** + DB엔 경로·메타(`model_registry`) | 바이너리는 DB에 직접 X |
| **대용량 시퀀스** | **npz/parquet + 경로** (DB JSONB ❌) | 12에서 지적한 안티패턴 회피 |
| Colab 실험 캐시 | 파일/Drive | 기준 데이터는 항상 DB |
- **누수 방지(불변)**: 스케일러·인코더·이벤트ID 매핑은 **train 구간에서만 fit**, DB/Colab/Vercel은 동일 artifact로 **transform만**.
- DB 스키마 변경은 **반드시 문서와 함께**(Colab·Streamlit·API가 모두 의존).

## 4. 정합성 결론

| 축 | 결정 | 12와의 관계 |
| --- | --- | --- |
| API | Vercel API **얇게** 구축 | 모순 아님 — "형식주의 말고 최소로" |
| 계층 | **실용적 L2+**(폴더/함수 분리), 풀 DDD 생략 | 12의 "L2 권장"과 일치 |
| 인프라 | **DB 단일원천 + 파일 보조** | 12의 "누수 방지·경계 합의" 그대로 적용 |

→ **모순이 아니라 단계 진화**다: 12는 *형식주의 경고*, 05-3은 *결정된 요구의 올바른 구현 수준*을 정한다. 한 줄 규칙: **"인프라는 두되, 도메인/Protocol 같은 형식 계층은 만들지 않고, 경계 합의·누수 방지·단일책임만 지킨다."**
