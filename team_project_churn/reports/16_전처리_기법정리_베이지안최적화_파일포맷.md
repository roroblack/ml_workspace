# 16. 데이터 전처리 — 기법 정리 · 베이지안 최적화 · 파일 위치/포맷/압축

대상: `sample_project` **실제 REES46(2019-Nov, 사용자 8천 표본 → 모집단 3,911명, 이탈률 81.9%)**.
코드: `preprocess_bayes.py`(전처리 베이지안 최적화·포맷 측정), `preprocess_bayes2.py`(범주형 인코딩·임베딩 비교 + 모델별 최적 전처리), `sample_project/src/build_features.py`(전처리). 지표 원본: `sample_project/outputs/preprocess_bayes.json`, `preprocess_bayes2.json`.

## 1. 사용된 전처리 기법 (전체 정리)

| 기법 | 적용 위치 | 내용 |
| --- | --- | --- |
| **시계열 라벨링(누수 차단)** | `build_features.py` | 관찰 14일 / 결과 7일, **결과기간 무활동=이탈(1)**. 피처는 관찰기간으로만 → 미래 누수 차단. 기준일은 데이터에서 자동 도출 |
| **집계 피처(RFM 계열)** | `build_features.py` | `groupby(user)` → recency_days·n_view·n_cart·n_purchase·n_events·active_days·avg_price |
| **결측 처리** | `build_features.py` | `reindex(users).fillna(0)` (비활동/이벤트없음 = 0) |
| **시퀀스화** | `build_features.py` | 일별 [view,cart,purchase] 카운트 → `[N,14,3]`, 비활동일 **0 패딩** |
| **스케일링(누수 차단)** | `train_ml.py`/`train_dl.py` | 정형=StandardScaler(train fit→test transform), 시퀀스=feature별 표준화(train 통계). predictor는 **transform만** |
| **층화 분할** | `train_ml.py`/`train_dl.py` | `train_test_split(stratify=y)`, 동일 SEED로 ML/DL 일관 |
| **클래스 불균형 대응** | ML/DL | LogReg `class_weight=balanced`, DL `BCEWithLogitsLoss(pos_weight)` |

**참고(다른 데이터 버전)**: Bank Churn 버전([01 결과서](01_데이터_전처리_결과서.md))엔 **원-핫 인코딩 + IQR 이상치 점검**까지 포함. 샘플(REES46)은 피처가 수치형이라 인코딩 생략.
**현재 안 쓴 것**: 범주형 인코딩/임베딩(→ **3장에서 실측: 도움 안 됨, 임베딩은 오히려 하락**), SMOTE(대신 class_weight), IQR 클립(점검만, 최적에서 탈락).

## 2. 베이지안 최적화로 찾은 최적 전처리 조합

전처리 *조합*을 optuna(TPE)로 탐색. **모델은 LogReg로 고정**(전처리 효과를 분리하기 위해), **5-fold Stratified CV의 ROC-AUC**로 평가, **누수 차단**(스케일러/SMOTE를 폴드별 Pipeline 내부에서 fit).

**탐색 공간**

| 전처리 | 후보 |
| --- | --- |
| 스케일러 | standard / minmax / robust / none |
| 카운트 로그변환(log1p) | 사용 / 미사용 |
| IQR 이상치 클립 | 사용(k=1.5~3.0) / 미사용 |
| 불균형 처리 | none / class_weight / SMOTE |

**결과 (실제 REES46, 40 trials)**

| 구분 | 전처리 | CV AUC |
| --- | --- | --- |
| 기준(baseline) | StandardScaler + class_weight | 0.7296 |
| **베이지안 최적** | **MinMaxScaler + log1p(카운트) + class_weight** (IQR 미사용) | **0.7553** |
| 개선폭 | | **+0.0257** |

**해석**
- **카운트 피처가 right-skew** → `log1p`가 분포를 안정화해 효과(가장 큰 기여).
- **선형 모델(LogReg)엔 MinMax**가 Standard보다 잘 맞음(0~1 범위).
- **class_weight**로 82% 불균형 대응. **SMOTE는 최적에서 탈락**(여기선 class_weight가 더 안정).
- **IQR 클립은 미채택** — recency/카운트의 큰 값이 의미 있는 신호라 자르면 손해.

→ **결론: 전처리 조합만 바꿔도 AUC +0.026**(작지 않음). 즉 *"스케일러 기본값"보다 "log1p + MinMax + 불균형가중"이 이 데이터엔 최적*. (산출물 `outputs/preprocess_bayes.json`에 상위 trial 기록)

## 3. 범주형 인코딩 비교 — "왜 임베딩이 후보에 없었나"

코드: `preprocess_bayes2.py` / 산출물: `sample_project/outputs/preprocess_bayes2.json`.

### 3.1 왜 처음엔 임베딩이 후보에 없었나
- **2장의 베이지안 탐색은 "정형(tabular) 피처 + 선형/트리 모델"** 조합이었습니다. 임베딩(`nn.Embedding`)은 **신경망 안에서만 학습되는 레이어**라 LogReg/GBM 파이프라인엔 끼워넣을 수 없습니다 → 같은 비교 테이블에 못 올립니다.
- 또 샘플 피처는 **이미 수치형 집계(RFM)** 라 인코딩 자체가 필요 없었습니다. 범주형(`category_id`·`brand`)은 build 단계에서 빼고 있었습니다.
- 임베딩의 강점은 **순서형 시퀀스(세션 단위 step feature)** 에서 나오는데, 이 라벨(14일 관찰 → recency형 이탈)은 **순서보다 "최근 활동량"이 지배적**이라 임베딩이 빛나는 구조가 아닙니다(리포트 11의 base/A/B/C 결론과 동일).

→ **그래서 "후보에서 빠진 게 아니라, 같은 표에 못 올라가는 다른 축"** 이었습니다. 그래서 **이번에 임베딩을 실제로 넣어 별도 비교**를 했습니다.

### 3.2 실측 결과 — 사용자별 대표 `category_id`·`brand`를 추가해 6가지 방식 비교
(5-fold CV AUC, 같은 정형피처 + 범주형 인코딩만 교체. embed_MLP는 torch `nn.Embedding`)

| 방식 | 인코딩 | 모델 | CV AUC |
| --- | --- | --- | --- |
| **num_MLP** | 범주형 미사용(수치만) | MLP | **0.7566** |
| num_GBM | 범주형 미사용(수치만) | GBM | 0.7503 |
| onehot_GBM | 원-핫 | GBM | 0.7496 |
| freq_GBM | 빈도(frequency) | GBM | 0.7486 |
| target_GBM | 타깃(mean, CV-safe) | GBM | 0.7214 |
| **embed_MLP** | **임베딩(nn.Embedding)** | MLP | **0.6800** |

**해석 (핵심)**
- **범주형을 어떻게 인코딩해도 수치-only보다 나아지지 않음.** onehot/freq는 수치-only와 동률, target은 오히려 하락(과적합), **임베딩은 최하(0.68)**.
- **임베딩이 가장 나쁜 이유**: ① 표본 3,911명에 임베딩 파라미터(category 320×16 + brand 157×8)가 과해 **과적합**, ② "사용자별 대표 1개 카테고리"로 축약하며 **정보 손실**, ③ **순서형 신호가 없는 라벨**이라 임베딩이 잡을 구조 자체가 없음.
- 즉 **"임베딩이 항상 우월하다"는 통념이 이 과제에선 반례** — recency 지배형 이탈엔 *집계 수치 + 트리/단순 MLP*가 임베딩을 앞섭니다. (임베딩은 세션/시퀀스 라벨에서 써야 함 → 개선방향 6번)

## 4. 모델별 최적 전처리 (전처리×모델 공동 관점)

리포트 11에서 쓴 모델군(LogReg·GBM·MLP)별로 **전처리 조합을 따로 베이지안 최적화**(각 20 trials). "모델마다 맞는 전처리가 다르다"는 가설의 실측.

| 모델 | 최적 전처리 | CV AUC |
| --- | --- | --- |
| **MLP** | robust + log1p(카운트) + class_weight | **0.7584 (전체 최고)** |
| LogReg | (스케일 없음) + log1p + class_weight | 0.7551 |
| GBM | robust + (로그 미사용) + 불균형처리 없음 | 0.7503 |

**해석**
- **트리(GBM)는 스케일·로그변환과 무관** — 로그 미사용·불균형처리 없음에서 최고. (스케일 불변성 확인)
- **선형/신경망(LogReg·MLP)은 log1p + 불균형가중이 필수** — right-skew 카운트를 펴주고 82% 불균형을 보정해야 성능이 오름.
- **전체 1위는 MLP(0.7584)**, 근소차로 LogReg(0.7551). GBM은 추가 범주형 없이도 0.75 — 안정적.
- → **"모델군별 전처리 분기"가 실측으로 정당화됨**. 단일 전처리를 모든 모델에 강요하면 손해.

## 5. 추가 개선 방향

1. **범주형 활용(검증 완료, 3·4장)**: 단순 추가는 효과 없음(임베딩은 오히려 하락). → 파생 피처화(아래 2번)나 **순서형 시퀀스에서의 임베딩**(6번)으로만 가치가 있음.
2. **파생 피처**: 카테고리 다양성, 브랜드 집중도(엔트로피/HHI), 가격대(평균/프리미엄 비율), view→cart→purchase 전환율.
3. **시간 기준 분할(temporal split)**: 현재 랜덤 층화 → 시계열 누수에 더 엄격한 시간 분할로.
4. **불균형 심화**: 분류 **임계값 최적화**(F1/비용 기반), focal loss, SMOTE 변형(BorderlineSMOTE).
5. **모델별 전처리 분기(검증 완료, 4장)**: 실측 결과 GBM은 스케일·로그 무관, LogReg/MLP는 log1p+불균형가중 필수 → 모델군별 파이프라인 적용 권장.
6. **시퀀스 전처리**: category 임베딩을 step feature로, 윈도우 길이·세션화 기준 튜닝, train/serve 윈도우 정합화.
7. **베이지안 탐색 확장**: 모델 하이퍼파라미터까지 공동 최적화(현재는 전처리만, 모델 고정).

### 6.2 포맷별 용량 비교 (압축이 중요한 이유)

**정형 피처(features.csv 기준)**

| 형식 | 용량 | 메모 |
| --- | --- | --- |
| CSV | 215.7 KB | 가독성↑, 타입 손실·느림 |
| **CSV + gzip** | **61.0 KB** | 공유/전송용 최소(약 3.5배↓) |
| **Parquet(snappy)** | **93.2 KB** | **컬럼형·타입 보존·빠른 읽기** → 파이프라인 권장 |

**시퀀스(`[3911,14,3]`, 0 비율 96%)** ★핵심

| 형식 | 용량 | 메모 |
| --- | --- | --- |
| npy(비압축) | 641.8 KB | |
| `np.savez`(비압축 zip) | 641.9 KB | **압축 아님**(흔한 오해) |
| **`np.savez_compressed`** | **16.0 KB** | **약 40배↓** (희소·0 많음) |

> **시퀀스는 0이 96%라 압축 효과가 폭발적**입니다. 기존 코드가 `np.savez`(비압축)였던 것을 **`np.savez_compressed`로 변경 적용**(642KB → 16KB).

### 6.3 권고
- **정형 피처**: 파이프라인 내부 = **Parquet**(타입·속도), 공유/제출 = **CSV.gz**, 사람이 볼 샘플만 CSV.
- **시퀀스/배열**: **`np.savez_compressed`**(또는 parquet/feather). 절대 `np.savez`(비압축) 방치 금지.
- **DB(Neon)**: 대용량 시퀀스는 **DB에 넣지 말고 파일(압축)+경로**(05-5 원칙). 원본 이벤트(10MB+)도 파일.
- **원본 이벤트**: 보관/이관 시 **parquet**(같은 데이터 CSV 대비 수배 작고 빠름).
