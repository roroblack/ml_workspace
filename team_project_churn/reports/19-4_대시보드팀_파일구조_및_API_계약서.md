# 19-4. 대시보드팀 파일구조 및 API 계약서

기준 문서: [19-2](19-2_최종_백엔드_설계도.md), [19-3](19-3_모델팀_산출물_및_I_O_계약서.md), [27](27_시각화자료_핵심8개_선정리포트.md), [05-6-4](05-6-4_프로그램_구조도_및_함수_변수_비전_명세서.md)

본 문서는 대시보드 담당자가 **어떤 파일을 만들고, 어디에 저장하고, 어디서 데이터를 불러오고, 어떤 JSON 형태를 기대해야 하는지**를 명시한다.

---

## 1. 핵심 결론

| 구분 | 결정 |
| --- | --- |
| 대시보드 위치 | `dashboard_streamlit/` |
| 화면 프레임워크 | Streamlit |
| 데이터 원천 | FastAPI 백엔드 REST |
| 운영 DB 직접 접속 | 금지 |
| Neon 직접 접속 | 금지 |
| 모델 artifact 직접 로드 | 금지 |
| 모델 평가 파일 직접 읽기 | 운영 금지, 개발 mock만 허용 |
| 역할 처리 | 기본값 `customer`, 화면 분기에는 사용하지 않음 |
| 대시보드 화면 | 고객/관리자/개발자 화면 분리 없이 단일 통합 대시보드 |
| 시각화 수신 | 15개 후보 전체 수신 가능, 화면에서는 확정본만 선택 표시 |

대시보드팀은 **데이터를 계산하지 않고 표시한다.**  
계산·집계·모델 평가·DB 조회는 백엔드가 담당하고, 대시보드는 백엔드가 주는 chart-ready JSON을 화면에 그린다.

## 2. 대시보드 담당자 작업 범위

| 해야 하는 일 | 하지 않는 일 |
| --- | --- |
| Streamlit 화면 구성 | MySQL 직접 query |
| 백엔드 REST 호출 | Neon 직접 query |
| 응답 JSON 검증 후 렌더링 | 모델 학습/추론 직접 실행 |
| 단일 통합 대시보드 구성 | `models/churn/*` artifact 직접 로드 |
| 개발용 mock JSON 작성 | `data/processed/evaluation/*` 운영 직접 읽기 |
| API 오류/로딩/빈 데이터 상태 처리 | metric, PR-AUC, lift 직접 계산 |

운영 구조:

```text
dashboard_streamlit
-> backend FastAPI REST
-> MySQL / Neon / files
```

개발 중 백엔드가 준비되지 않았을 때만 `dashboard_streamlit/mocks/`를 사용한다.

## 5. 백엔드 API 호출 계약

대시보드는 아래 endpoint만 호출한다.

| 화면 | Endpoint | Method | 용도 |
| --- | --- | --- | --- |
| 공통 | `/health` | GET | 백엔드 상태 확인 |
| 공통 | `/models/active` | GET | active 모델 목록 |
| 로그인 | `/auth/face/check-id?user_id=` | GET | ID 중복 확인(교육과제②) → `{user_id, exists, available}` |
| 로그인 | `/auth/face/register` | POST(**multipart**) | 얼굴 등록. **이미지 업로드** → 백엔드가 임베딩 → `face_user` 생성 |
| 로그인 | `/auth/face/login` | POST(**multipart**) | 얼굴 로그인. **이미지 업로드** → 백엔드 임베딩·매칭 → `face_login_log` 저장 |
| 로그인 | `/auth/me` | GET | 현재 사용자 정보 조회 |

> **(2026-06-22 정정 — BUG-001)** register/login은 **`multipart/form-data`** 다. 대시보드(클라이언트)는 OpenCV로 **얼굴 검출(bbox)만** 하고 **이미지 파일을 그대로 업로드**한다(form: `image`(file), `user_id`, `display_name`, `role`, `face_bbox`). **512d 임베딩(insightface)·매칭은 백엔드**가 수행한다(19-4 §1: 대시보드=표시 계층, 무거운 ML=백엔드). 초기 설계에서 임베딩 주체가 불명확해 백엔드가 "클라이언트 임베딩 JSON 수신"으로 잘못 구현됐던 것을 본 계약으로 확정·정정한다.
| 통합 | `/dashboard/summary` | GET | 전체 KPI |
| 통합 | `/dashboard/charts/:chartName` | GET | 시스템/데이터/cohort/baseline 등 모델 비종속 chart JSON |
| 통합 | `/predictions/top-risk` | GET | 고위험 고객 목록 |
| 통합 | `/models/:modelId/evaluation` | GET | 모델 평가 요약 |
| 통합 | `/models/:modelId/charts/:chartName` | GET | 15개 시각화 후보 chart JSON |
| 통합 | `/dashboard/user/:userId` | GET | 유저 개인 대시보드 |
| 통합 | `/predictions/latest?user_id={userId}` | GET | 유저 최신 이탈 확률 |
| 통합 | `/recommendations/:userId` | GET | 유저 추천 결과 |
| 운영 | `/retention-actions` | POST | 리텐션 액션 기록 |

대시보드는 API 응답을 그대로 그린다. 응답이 비었거나 실패하면 계산으로 메우지 않고 빈 상태 UI를 보여준다.

## 6. 공통 API 응답 형태

모든 대시보드용 API는 아래 wrapper를 권장한다.

```json
{
  "ok": true,
  "data": {},
  "meta": {
    "schema_version": "dashboard.v1",
    "generated_at": "2026-06-21T00:00:00+09:00",
    "source": "backend"
  },
  "error": null
}
```

오류:

```json
{
  "ok": false,
  "data": null,
  "meta": {
    "schema_version": "dashboard.v1"
  },
  "error": {
    "code": "BACKEND_UNAVAILABLE",
    "message": "backend API is not reachable"
  }
}
```

`api_client.py`는 `ok=false` 또는 HTTP 오류를 `components/error_state.py`로 넘긴다.

## 7. 화면별 데이터 계약

### 7.1 로그인 화면

파일:

```text
pages/01_face_login.py
services/auth_service.py
```

session state:

| key | dtype | 설명 |
| --- | --- | --- |
| `is_logged_in` | bool | 로그인 여부 |
| `user_id` | str | 로그인 사용자 ID |
| `display_name` | str | 표시 이름 |
| `role` | str | 기본 `customer`, 화면 분기에는 사용하지 않음 |
| `access_token` | str/null | API 인증 토큰, 개발 단계에서는 null 가능 |

화면 이동:

```text
로그인 성공 -> 02_dashboard.py
role 값이 없으면 customer로 저장
```

`face_user`와 `face_login_log`는 대시보드가 직접 읽지 않는다. 현재 구조에서 두 테이블은 **백엔드가 MySQL에서 읽고 쓴다**.

```text
대시보드: 카메라 촬영 → OpenCV 얼굴 검출(bbox)만 → 이미지 파일 업로드(multipart)
-> backend /auth/face/register 또는 /auth/face/login
-> backend.infrastructure.face.embedder (insightface buffalo_l → 512d 임베딩)   ← 임베딩은 백엔드
-> backend.infrastructure.mysql.face_repository
-> MySQL face_user 조회/생성(embedding 저장) · face_login_log insert
-> {user_id, display_name, role="customer"} 반환
-> dashboard_streamlit session_state 저장
```

정리:
- **임베딩(512d)·얼굴 매칭은 백엔드**(`infrastructure/face/embedder.py`, insightface). 대시보드는 검출(bbox)만 하고 이미지를 올린다(19-4 §1).
- `face_user`: 백엔드가 MySQL에서 조회/생성(embedding LONGBLOB 저장).
- `face_login_log`: 백엔드가 로그인 성공/실패 결과를 MySQL에 저장한다.
- ID 중복은 `/auth/face/check-id`로 사전 확인(교육과제②).
- 대시보드는 `/auth/*` 응답만 받는다.
- `role`은 기본 `customer`이며 별도 관리자/개발자 화면 분기에는 사용하지 않는다.

### 9.9 나머지 chart

위 예시는 대표 schema다. 15개 chart는 모두 9.1의 공통 wrapper를 따르고, `chart_name`, `chart_type`, `x`, `y`, `data`, `summary`만 chart 성격에 맞게 바꾼다.

| chart_name | 권장 chart_type | 필수 data key |
| --- | --- | --- |
| `system_architecture` | image/spec | `nodes`, `edges` 또는 `asset_path` |
| `data_distribution` | histogram/bar | `feature`, `bin`, `count` |
| `cohort_retention` | heatmap | `cohort`, `week_index`, `retention_rate` |
| `baseline_comparison` | bar/table | `model_name`, `pr_auc`, `roc_auc`, `f1` |
| `train_val_loss` | line | `epoch`, `train_loss`, `val_loss` |
| `pr_auc` | line | `recall`, `precision`, `threshold` |
| `roc_auc` | line | `fpr`, `tpr`, `threshold` |
| `score_distribution` | histogram | `bin`, `churn_count`, `non_churn_count` |
| `threshold` | line | `threshold`, `precision`, `recall`, `f1` |
| `confusion_matrix` | matrix | `actual`, `predicted`, `count` |
| `lift` | line | `top_percent`, `capture_rate`, `lift` |
| `calibration` | line | `prob_pred`, `prob_true`, `count` |
| `shap_summary` | bar | `feature`, `mean_abs_shap`, `rank` |
| `value_at_risk` | treemap/bar | `segment`, `value_at_risk`, `users` |
| `revenue_recovery` | bar | `top_percent`, `value_at_risk`, `expected_recovery` |

## 11. 구현 순서

```text
1. dashboard_streamlit/ 폴더 생성
2. app.py, .env.example, .streamlit/config.toml 작성
3. services/api_client.py 작성
4. auth API mock과 15개 chart mock JSON 먼저 작성
5. components/charts.py에 15개 chart 렌더 함수 작성
6. pages/01_face_login.py 작성
7. pages/02_dashboard.py 작성
8. 단일 통합 대시보드 안에서 개인/운영/모델진단/비즈니스 탭 구성
9. DASHBOARD_USE_MOCK=true로 화면 완성
10. 백엔드 준비 후 DASHBOARD_USE_MOCK=false로 전환
11. /auth/*, /health, /dashboard/summary, /models/:id/charts/* 연동 확인
```

## 12. 제출 전 체크리스트

대시보드 담당자는 제출 전 아래를 확인한다.

| 체크 | 항목 |
| --- | --- |
| [ ] | `dashboard_streamlit/app.py`로 실행 가능하다 |
| [ ] | MySQL/Neon에 직접 접속하는 코드가 없다 |
| [ ] | 모델 artifact를 직접 로드하는 코드가 없다 |
| [ ] | 모든 API 호출은 `services/api_client.py`를 통한다 |
| [ ] | `role`이 없으면 `customer` 기본값이 적용된다 |
| [ ] | `role=admin/developer` 기준 별도 대시보드 파일이 없다 |
| [ ] | 단일 통합 대시보드에 개인/운영/모델진단/비즈니스 탭이 있다 |
| [ ] | 15개 시각화 후보를 모두 API/mock에서 받아올 수 있다 |
| [ ] | 확정된 핵심 시각화만 기본 노출하고 나머지는 선택/부록 탭으로 숨길 수 있다 |
| [ ] | 최신 이탈 확률, 위험등급, 추천/리텐션 액션이 있다 |
| [ ] | API 실패/빈 데이터 상태 UI가 있다 |
| [ ] | Mock JSON과 실제 API 응답 schema가 같다 |
| [ ] | `DASHBOARD_USE_MOCK=false`일 때 백엔드 REST로 동작한다 |
