# Part 1. 라이브 사이트 없이 "실시간" 예측을 구현·검증하는 법

## 핵심 발상
**실시간 예측 = "이벤트가 도착하는 순서대로 처리"** 일 뿐입니다. 운영 사이트가 만드는 이벤트 스트림은,
우리가 가진 **과거 로그(REES46)를 시간순으로 한 건씩 흘려보내면(replay)** 똑같이 재현됩니다.
→ **웹사이트 없이도 "실시간 동작"을 100% 검증·시연**할 수 있습니다.

## 방법 1 — 인과적(causal) 모델 + 조기 학습 (오프라인 학습)
- 시점 t는 **이벤트 1..t만** 보게 함(미래 누수 금지): 단방향 LSTM/GRU 또는 causal-mask Transformer.
- 학습: **스텝별 출력(many-to-many)** — 매 시점이 세션 최종 결과를 맞히도록 BCE. 자연스럽게 "일부만 보고도" 예측하는 능력 학습.
- (우리는 라벨 A의 세션 시퀀스 데이터가 이미 있어 이 모델만 바꿔 학습하면 됨.)

## 방법 2 — 스트리밍 재생 평가 ("조기성" 측정)
운영의 실시간 성능을 오프라인 로그로 그대로 측정:
- **정확도@k**: 이벤트 3개/5개/10개까지만 봤을 때의 AUC 곡선 → "몇 개 보면 충분히 정확한가".
- **경보까지 이벤트 수 / 시간**: 위험 임계 도달 시점의 평균.
- **조기 경보 정밀도**: 일찍 위험으로 표시한 세션이 실제로 이탈했는지.

## 방법 3 — 녹화 세션 데모 (사이트 대체) ★발표용
- **Streamlit/CLI 데모**: 저장된 세션 하나를 골라 **이벤트를 한 칸씩 "재생"**하며,
  화면에 **이탈 확률이 실시간으로 갱신**되고 임계 돌파 시 **"⚠️ 개입 트리거(쿠폰 발송)"** 표시.
- 슬라이더/버튼으로 t를 늘려가며 확률 변화를 보여주면 = **실시간 동작을 그대로 시연**. (웹서비스 불필요)

## 방법 4 — 개입 효과는 "정직하게" 다루기
- 진짜 개입 효과(쿠폰 보내면 전환↑)는 **실험(A/B)** 이 있어야 인과적으로 증명됨 → 사이트·트래픽 없으면 불가.
- 대신 **예측 품질 + 타겟팅 시뮬레이션**으로 대체: "고위험 상위 X%를 조기에 잡았을 때 포착되는 이탈 세션 비율 / 절감 가능 매출(가정)". → *예측 가치*는 보이되 *인과 효과는 가정*임을 명시.

## 구현 로드맵 (오프라인, 우리 데이터로 가능)
1. 라벨 A 세션 시퀀스 재사용 → **causal LSTM(스텝별 출력)** 학습
2. **정확도@k 곡선** + 정형 GBM(같은 시점 집계)과 비교
3. **Streamlit 재생 데모**(세션 선택 → 이벤트 재생 → 확률·개입 시각화)
→ 결론: **사이트 없이도 "조기에·더 정확히 잡는다"를 수치+데모로 제출 가능.**

# Part 2. 팀 협업용 클린아키텍처 "개념 가이드" (가볍게 적용)

## 전제 — "도입"이 아니라 "개념 공유"
2일 ML 팀 프로젝트에서 **FastAPI·풀 클린아키텍처를 구축할 필요는 없습니다.** 목적은 *웹서비스*가 아니라
**협업이 매끄럽고 코드가 정리되는 것**. 그래서 그 밑의 **원칙만** 가져와 가볍게 적용합니다. (가이드 원문: `fastapi-clean-architecture-guide.md`)

## 팀과 공유할 핵심 원칙 5가지 (프레임워크 없이도 적용)
1. **관심사 분리(SoC)**: 데이터 / 전처리 / 모델 / 평가 / (선택)서빙을 **파일·함수로 분리**. → 우리 `src/`가 이미 이 형태(`preprocess.py`, `train_ml.py`…).
2. **경계 먼저 합의(interface-first)** ★협업 핵심: 코드보다 **계약**을 먼저 정함 — *처리된 데이터 스키마, 모델 인터페이스 `predict(X)->proba`, metrics.json 포맷*. 정해지면 팀원이 **서로 안 기다리고 병렬 작업**.
3. **의존성 방향**: 핵심 로직(라벨 정의·지표 계산)은 **순수 함수**로, 파일 입출력/경로 같은 세부에 안 묶이게. → 테스트·교체 쉬움.
4. **단일 책임**: 파일 1개 = 역할 1개. 새 기능은 기존 슬라이스 복제.
5. **경계에서 변환**: 원본 컬럼명·DB 모델이 모델/지표 코드로 새지 않게(식별자 제외 등). → *우리가 겪은 `user_id` 누수 버그가 이 원칙 위반 사례*.

## 우리 프로젝트에 "가볍게" 적용 (레벨 선택)
| 레벨 | 형태 | 우리 채택 |
| --- | --- | --- |
| L1 미니멀 | 스크립트 1~2개 | 너무 단순 |
| **L2 권장** | `data→features→model→eval` 모듈 분리 + 경계 합의 | **★우리 수준** |
| L3 풀스펙 | domain/Protocol/DI까지 | 과함(2일엔 불필요) |
→ **L2면 충분.** 지금 `team_project_churn/` 구조가 사실상 L2입니다.

## 협업 규약 (이게 실질 가치)
- **0일차 경계 회의**: 데이터 스키마·모델 인터페이스·지표 포맷 먼저 합의해 머지
- **수직 분배**: 사람마다 파일/도메인 소유 → 머지 충돌 최소
- **브랜치/PR**: `feat/preprocess` 등 기능 단위, main 보호, 1인 리뷰
- **노트북 규율**: `.ipynb`는 충돌 지옥 → `.py` 우선, 노트북은 1인1파일+출력 비우기
- **PR 체크리스트**: ① 식별자/누수 컬럼 제외 ② 스케일러 train에만 fit ③ 모델 바이너리 커밋 금지(.gitignore) ④ 재현 명령 통과
- **WORKLOG**: 작업/의사결정/실험 기록 ([reports/WORKLOG.md](WORKLOG.md))

## 팀 회의 토론 포인트 (이 가이드로 대화)
1. 우리 경계 산출물(스키마·인터페이스·지표)은 무엇으로 고정할까?
2. 누가 어떤 슬라이스를 소유할까(수직 분배)?
3. 노트북 vs 스크립트, 브랜치 규칙은?
4. "도메인 순수 함수"로 둘 핵심 로직(라벨 정의·지표)은 무엇?

## "응용" 가벼운 실습 아이디어
- 현재 `predict.py`를 **L2 구조로 리팩터**: `load_model()`(repository) / `predict_proba()`(service) / 입력검증(presentation) 함수로 분리해 보기 — FastAPI 없이 **개념만** 체득.
- 또는 추론을 **간단 함수형 서비스**로 감싸 단위 테스트(가짜 모델 주입) 작성 → "의존성 주입/테스트 용이성"을 코드로 느끼기.

## 결론
- **(1)** 사이트가 없어도 **로그 재생(replay) + causal 모델 + Streamlit 데모**로 "세션 중도 실시간 예측"을 구현·시연·평가할 수 있습니다(개입의 *인과 효과*만 가정으로 처리).
- **(2)** 클린아키텍처는 *구축*이 아니라 **협업 원칙 공유**로 가져가면 됩니다. **L2(모듈 분리 + 경계 합의) + 협업 규약**이 2일 팀 프로젝트의 최적점이고, 우리 구조가 이미 거기에 가깝습니다.
