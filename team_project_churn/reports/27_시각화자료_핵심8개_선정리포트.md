# 27. 시각화 자료 핵심 8개 선정 리포트

기준 문서: [19-2](19-2_최종_백엔드_설계도.md), [19-3](19-3_모델팀_산출물_및_I_O_계약서.md), [26-0](26-0_가지마_대시보드_구축_단계별_계획서.md)

기존 15개 시각화 후보를 발표·대시보드 필수 자료 기준으로 절반 수준인 **핵심 8개**로 축소한다. 목적은 "많이 보여주기"가 아니라, 이탈 문제 이해 -> 모델 성능 증명 -> 운영 가능성 -> 비즈니스 가치까지 끊기지 않는 흐름을 만드는 것이다.

구현 계약은 별도다. 백엔드와 대시보드는 15개 후보를 모두 받을 수 있게 만들고, 실제 기본 화면/발표 화면에서만 아래 핵심 8개를 우선 노출한다. 나머지 7개는 선택 탭 또는 부록 탭으로 보관한다.

---

## 1. 선정 기준

| 기준 | 설명 |
| --- | --- |
| 발표 설득력 | 비전공자도 왜 필요한지 바로 이해할 수 있는가 |
| 모델 검증력 | 모델이 실제로 분리·예측을 잘하는지 보여주는가 |
| 운영 의사결정 | threshold, 캠페인 대상 선정, 신뢰도 판단에 직접 쓰이는가 |
| 구현 가능성 | 모델팀 산출물과 백엔드 chart API로 제공 가능한가 |

최종 선택은 **8개 유지 / 7개 부록 또는 제외**로 정리한다.

---

## 2. 최종 채택 8개

| 순서 | 시각화 | 구분 | 채택 이유 | 원천 산출물 |
| ---: | --- | --- | --- | --- |
| 1 | 시스템 아키텍처 | 셋업 | 프로젝트가 단순 모델이 아니라 시뮬 사이트·백엔드·DB·대시보드까지 연결된 운영 구조임을 보여줌 | `reports/19_mysql_erd_v6_reflected.svg`, 구조도 |
| 2 | Cohort Retention | 이탈 현상 이해 | 모델 전에 "왜 이탈 예측이 필요한가"를 설명하는 핵심 근거 | `cohort_summary.json` 또는 cohort 집계 parquet |
| 3 | 베이스라인 비교 | 모델 검증 | LSTM/Transformer와 LogReg/XGB/GBM 계열 비교로 최종 모델 선택 근거 제시 | `metrics_summary.json`, `model_evaluation` |
| 4 | PR-AUC | 모델 검증 | 불균형 데이터에서 주지표 역할. 모델 성능을 가장 압축적으로 설명 | `threshold_curve.json` 또는 PR curve artifact |
| 5 | Threshold P/R/F1 | 운영 기준 | 어느 확률 이상을 고위험으로 볼지 결정하는 운영 임계값 근거 | `threshold_curve.json` |
| 6 | Lift Chart | 타겟팅 효율 | 상위 N% 고객에게 개입했을 때 얼마나 효율적인지 보여줌 | `lift_curve.json` |
| 7 | Calibration | 운영 신뢰성 | "0.8점이면 진짜 80% 수준인가"를 확인해 운영 점수 신뢰도를 설명 | `calibration_curve.json` |
| 8 | Revenue Recovery Simulation | 비즈니스 가치 | 모델이 매출 회복/이탈 방지 액션으로 이어진다는 최종 가치 제시 | `business_value.json` |

---

## 3. 제외 또는 부록 처리 7개

| 기존 번호 | 시각화 | 처리 | 이유 |
| ---: | --- | --- | --- |
| 2 | 데이터 분포 | 부록 | 데이터 품질 설명에는 좋지만, 핵심 발표 흐름에서는 Cohort Retention이 더 직접적 |
| 5 | Train / Val Loss | 부록 | DL 모델 학습 안정성 확인용. 7모델 전체 비교 핵심 자료로는 약함 |
| 7 | ROC-AUC | 부록 | 보조지표로 유지 가능하지만, 불균형 데이터에서는 PR-AUC가 더 직접적 |
| 8 | Churn Score Distribution | 제외/부록 | 모델 분리 확인에는 유용하나 Threshold와 Lift가 운영 판단을 더 잘 설명 |
| 10 | Confusion Matrix | 부록 | 단일 threshold 결과 확인용. Threshold P/R/F1 그래프가 더 많은 정보를 제공 |
| 13 | SHAP Summary | 부록 | 설명력은 좋지만 현재 SHAP 환경 이슈와 대체 중요도 사용 가능성을 고려해 필수에서 제외 |
| 14 | Value at Risk Treemap | 부록 | Revenue Recovery Simulation과 메시지가 겹침. 발표 핵심은 회복 가능 금액으로 통일 |

## 4. 발표 흐름 권장안

```text
1. 시스템 아키텍처
   -> 우리가 만든 운영형 시스템 전체 그림

2. Cohort Retention
   -> 실제로 시간이 지나며 고객이 빠지는 문제 확인

3. 베이스라인 비교
   -> 여러 모델 중 어떤 모델이 강한지 비교

4. PR-AUC
   -> 불균형 데이터에서 모델 성능 검증

5. Threshold P/R/F1
   -> 어느 점수부터 고위험으로 볼지 결정

6. Lift Chart
   -> 상위 위험군 타겟팅 효율 확인

7. Calibration
   -> 예측 확률을 운영 점수로 믿을 수 있는지 확인

8. Revenue Recovery Simulation
   -> 이탈 방지 액션이 매출 회복으로 연결되는지 제시
```

이 순서면 "시스템을 만들었다"에서 끝나지 않고, "왜 필요한가 -> 잘 맞는가 -> 운영 가능한가 -> 돈이 되는가"까지 한 번에 이어진다.

## 6. 모델팀 필수 산출물 영향

15개 후보를 모두 받을 수 있게 하되, 핵심 8개를 우선 제공하려면 모델 담당자는 아래 파일을 먼저 안정화한다.

| 산출물 | 필수 여부 | 쓰이는 시각화 |
| --- | --- | --- |
| `metrics_summary.json` | 필수 | 베이스라인 비교, PR-AUC 요약 |
| `eval_predictions.parquet` | 필수 | PR-AUC, Threshold, Lift, Calibration 재계산 |
| `threshold_curve.json` | 필수 | Threshold P/R/F1 |
| `lift_curve.json` | 필수 | Lift Chart |
| `calibration_curve.json` | 필수 | Calibration |
| `business_value.json` | 필수 | Revenue Recovery Simulation |
| `cohort_summary.json` | 권장 | Cohort Retention |
| `shap_summary.json` | 부록 | SHAP Summary |

`19-3`의 모델팀 I/O 계약에서 위 파일을 모델별 평가 폴더에 저장하도록 유지한다.

```text
data/processed/evaluation/churn/{model_key}/
├── metrics_summary.json
├── eval_predictions.parquet
├── threshold_curve.json
├── lift_curve.json
├── calibration_curve.json
├── business_value.json
└── cohort_summary.json
```

## 7. 최종 결론

최종 발표와 대시보드의 핵심 시각화는 아래 8개로 고정한다.

```text
1. 시스템 아키텍처
2. Cohort Retention
3. 베이스라인 비교
4. PR-AUC
5. Threshold P/R/F1
6. Lift Chart
7. Calibration
8. Revenue Recovery Simulation
```

나머지 7개는 시간이 남을 때 부록으로 둔다. 특히 ROC-AUC, Confusion Matrix, SHAP Summary는 질문 대응용으로 보관하고, 메인 발표 흐름에는 넣지 않는다.
