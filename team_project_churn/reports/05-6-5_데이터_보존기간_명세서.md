# 05-6-5. 데이터 보존기간(Retention) 명세서

기준: 2026-06-22. 운영 DB(MySQL `project2db`)와 메모리 상태의 **모든 저장소별 보존정책**을 명시한다. 무한 증가(disk/RAM bloat) 방지 + 감사/이력 보존의 균형. 구현: `backend/app/infrastructure/mysql/retention.py`(시간기반 TTL + 스케줄러), `app/application/sim_usecase.py`(세션 idle).

기준 문서: [05-6-4](05-6-4_프로그램_구조도_및_함수_변수_비전_명세서.md) · [19-2](19-2_최종_백엔드_설계도.md) · `backend/db/schema_mysql.sql`

## 1. 보존정책 분류
| 분류 | 의미 | 정리 방식 |
| --- | --- | --- |
| **영구(Permanent)** | 운영 마스터. 키/upsert로 관리되어 무한 증가 안 함 | 정리 없음(갱신만) |
| **갱신(Replace)** | 항상 최신 1건만 유지 | 재기록 시 이전 삭제 |
| **TTL(기간보존)** | 로그·이력. 보존기간 초과분 삭제 | 스케줄러가 주기 DELETE |
| **RAM(세션)** | 메모리 상태 | LRU + idle 타임아웃 |
| **레거시** | 미사용(구버전) | 삭제 대상 |

## 2. 테이블별 보존기간 (운영 DB)

| 테이블 | 분류 | 보존기간 | 근거 |
| --- | --- | --- | --- |
| `model_registry` | 영구 | ∞ | 모델 마스터(`model_name` UNIQUE, upsert) |
| `model_evaluation` | 갱신 | 모델별 최신 1건 | 재제출 시 이전 평가 DELETE 후 INSERT |
| `prediction_log` | TTL | **90일** | 운영 예측 이력(추세/감사). 조회는 최신만 |
| `sim_event_log` | TTL | **7일** | 시뮬 이벤트=휘발성 |
| `retention_action_log` | TTL | **365일** | 리텐션 액션=비즈니스/감사 이력 → 장기 |
| `recommendation` | TTL | **90일** | 추천 결과 이력 |
| `feature_user_snapshot` | TTL | **90일** | 예측 시점 피처 스냅샷(재현용) |
| `face_login_log` | TTL | **90일** | 로그인 감사 로그 |
| `user_interest` | 영구 | ∞ | 유저 관심(PK=user_id, upsert·`updated_at`) |
| `face_user` | 영구 | ∞ | 계정 마스터(PK=user_id) |
| `sequence_snapshot` | 영구(경로) | ∞ | 시퀀스 파일 **경로 레지스트리**(대용량 파일은 DB 밖) |
| `ensemble_result` | TTL(예정) | **90일** | 앙상블 조합 이력. *구현 시 `ensemble_member` 선삭제(FK)* |
| `ensemble_member` | TTL(종속) | = ensemble_result | `ensemble_id` FK → result 따라감 |

## 3. 메모리(RAM) 보존
| 저장소 | 정책 |
| --- | --- |
| `_SESSIONS`(sim 세션) | **LRU 최대 500세션** + **idle 30분 만료**(`SESSION_IDLE_SEC`) |
| 세션당 `events` | **최대 300이벤트**(최근만) |
| `_mem`(memory 폴백) | predictions 1만·sim_events 5천 trim · 모델 캐시 lru(8)·tabular lru(1) |

## 4. 레거시 테이블(삭제 대상)
구 `app/db.py`(→`reports/reference/db_legacy/`)가 만든 잔재. 운영 백엔드 미사용 → DROP 권장.
- `churn_prediction` · `login_log` · `recommendation_log`

## 5. 구현 메커니즘 (현업 방식)
- **시간 기반 TTL**: `retention.cleanup_db()` 가 테이블별 `DELETE WHERE <ts_col> < NOW() - INTERVAL <days> DAY`.
- **스케줄러**: FastAPI `lifespan` 백그라운드 태스크 — **기동 시 1회 + 6시간마다**(`CLEANUP_INTERVAL_SEC`). DB 삭제는 `asyncio.to_thread`로 → **요청 경로(insert) 지연 0**.
- **세션 sweep**: 같은 스케줄러가 `sim_usecase.sweep_sessions()`로 idle 세션 제거.
- **수동 실행(ops)**: `POST /internal/cleanup`.
- insert 경로에서 DELETE하지 않는다(쓰기 지연·부정확 방지).

## 6. 환경변수(조정)
```env
RET_PREDICTION_DAYS=90
RET_SIM_DAYS=7
RET_ACTION_DAYS=365
RET_REC_DAYS=90
RET_LOGIN_DAYS=90
RET_SNAPSHOT_DAYS=90
CLEANUP_INTERVAL_SEC=21600   # 6h
SESSION_IDLE_SEC=1800        # 30m
```

## 7. 주의 — FK 의존성
- `retention_action_log.prediction_id → prediction_log.prediction_id`: prediction_log(90일)가 retention_action(365일)보다 짧음. **현재 `prediction_id`는 NULL로 적재**되어 충돌 없음. 만약 prediction_id를 채우면 **FK를 `ON DELETE SET NULL`로 변경**하거나 prediction_log 보존기간을 ≥ retention_action으로 둘 것.
- `ensemble_member.ensemble_id → ensemble_result`: ensemble TTL 적용 시 **member 선삭제** 필요.
- 삭제 실패(FK/일시오류)는 `cleanup_db`가 무시하고 다음 주기 재시도(크래시 없음).

## 8. 확장(대규모 시)
- 초대용량 로그: **월 RANGE 파티셔닝 → 오래된 파티션 DROP**(즉시·저부하).
- `sim_event_log`: 19-2 원설계대로 **Neon(별도 로그 DB) 분리**.
- 멀티워커: 세션을 **Redis 외부화**.
- 스케줄러: **APScheduler/외부 cron**으로 견고화.
