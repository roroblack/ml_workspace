## 1. 진단 — 데이터의 로깅 시간 단위

**REES46 원본 타임스탬프 = 초(second) 단위** (이벤트의 98.4%가 비-0 초값, 예 `2019-11-30 09:46:23`).
즉 **해상도 자체는 초단위로 충분**하다. 그런데 17-0/17-1의 모델은 이를 **일(day) 단위로 집계**해 실시간성을 버렸다.

실제 간격을 측정하면 두 개의 전혀 다른 시간 척도가 공존한다:

| 척도 | 측정값(실제 REES46) | 의미 |
| --- | --- | --- |
| **세션 내** 이벤트 간격 | 중앙 **18초**, p75 61초, p90 168초 (60초 이내 **70%**) | 한 방문 안에서는 초~분 단위로 촘촘 |
| **세션 사이** 간격 | p95 4.5시간, p99 138시간, **30분 초과 7%**(세션 경계) | 재방문은 며칠 단위 |
| 유저당 규모 | 중앙 **2 이벤트 / 1 세션** | 한 번 왔다 가는 유저가 다수 |

**결론(진단)**:
- 데이터는 초단위지만, **17-1의 churn 라벨("7일 무활동")은 본질적으로 며칠 단위의 느린 현상** → 초단위로 예측해도 라벨이 안 바뀌어 의미 없음. 그래서 일 집계가 합리적이었다.
- **초단위 실시간 개입이 의미를 가지려면 타깃을 바꿔야 한다**: "장기 churn"이 아니라 **"지금 이 세션에서 무구매로 이탈하려는 순간"**(세션 이탈 임박). 이건 세션 내 초~분 척도의 현상이다.
- 단, 실제 REES46는 유저당 세션이 너무 희소(중앙 1세션)해 **초단위 세션-이탈 모델을 모집단 규모로 학습하기 부족** → 측정 분포에 맞춘 **합성 다수유저 스트림**으로 시연한다.

## 2. 베스트 옵션 리서치 — "예측 간격을 얼마로?"

실시간 이탈방지 프로토콜이 **발동될 수 있을 만큼의 간격**을 정하는 게 핵심. 후보를 비교:

| 옵션 | 리드타임 | 개입 형태 | 비용/한계 |
| --- | --- | --- | --- |
| 일 단위 (17-0/17-1) | 수일 | 이메일 쿠폰·리타게팅(느린 리텐션) | 실시간 아님 |
| **이벤트 구동**(per-event) | 초~분 | exit-intent 팝업·실시간 쿠폰·챗 | **정보 도착시에만 스코어 → 효율적** |
| 고정 고빈도 tick (5초) | 초 | 동일 | 스코어링 낭비(유휴 유저에도 계속) |
| 고정 저빈도 tick (5분) | 분 | 동일 | 짧은 세션 놓침 |

**설계 결정**:
- **세션 정의**: 30분(1800초) 무활동 = 세션 종료 (GA 등 업계 표준, 측정상 간격>30분이 7%로 자연적 경계와 일치).
- **타깃 라벨**: *무구매 이탈 세션의 마지막 120초 이내 이벤트 = 임박 이탈(1)*. (리드타임 확보를 위해 종료 2분 전부터 양성)
- **스코어링 지연**: 측정 결과 단건 예측이 **GBM 0.17ms / LogReg 0.08ms** → 초당 6천~1.3만 건 스코어링 가능. **초단위 실시간은 모델 지연 측면에서 전혀 문제 없음**(병목은 모델이 아니라 이벤트 도착 빈도).

→ 따라서 **예측 간격은 "고정 시계(clock)가 아니라 이벤트 구동"이 베스트 후보**. 아래 실험으로 정량 검증.

## 3. 합성 초단위 스트림 (REES46 캘리브레이션)

- 세션 내 간격 ~ lognormal(median 18s, sigma 1.5) → 합성 p75≈49s/p90≈123s 로 실제(61/168)에 근사.
- 다수 유저가 6시간 horizon에 동시 브라우징. 이벤트 view→cart→purchase 전이, 구매성향 유저 45%.
- 이탈 확률은 이벤트마다 (세션 길어질수록↑, 뷰만 쌓이면↑, 카트 있으면↓)로 동적.

**생성 결과**: 세션 **6,000** · 이벤트 **30,668** · 무구매 이탈률 **65.1%** · 세션당 중앙 5 이벤트 · 임박이탈(양성) 38.1%.

## 4. 실시간 스코어러 — 모델 비교 (17-1과 동일 로스터: ML 3 + DL 3)

같은 임박-이탈 라벨에서 **ML 3종(러닝 집계 피처)** 과 **DL 3종(최근 12개 이벤트 시퀀스)** 을 동일 분할로 비교.
- ML 입력(러닝 집계): step, 경과시간, 직전 간격, 평균 간격, 간격비(직전/평균), n_view, n_cart, 카트보유, 카트후경과, 연속뷰.
- DL 입력(시퀀스): 최근 12 이벤트의 `[log1p(간격), is_view, is_cart]` → LSTM/GRU/Transformer.
- 세션 단위 70:30 분할(누수 차단), 양성(임박이탈) 38.1%.

| 구분 | 모델 | ROC-AUC | PR-AUC | 단건 지연 |
| --- | --- | --- | --- | --- |
| ML(집계) | **LogReg** | **0.7116** | 0.5709 | **0.08 ms** |
| ML(집계) | GBM | 0.7075 | 0.5645 | 0.17 ms |
| ML(집계) | MLP | 0.6994 | 0.5538 | ~0.1 ms |
| DL(시퀀스) | **LSTM** | 0.7114 | **0.5749** | ~수 ms |
| DL(시퀀스) | GRU | 0.7104 | 0.5746 | ~수 ms |
| DL(시퀀스) | Transformer | 0.7114 | 0.5747 | ~수 ms |

![model compare](../sample_project/outputs/realtime/model_compare.png)

**해석**
- **6종이 거의 동률.** ROC-AUC는 LogReg(0.7116)≈LSTM/Transformer(0.7114)로 사실상 같고, PR-AUC만 **DL이 근소 우위(0.575 vs LogReg 0.571, +0.004)**.
- **왜 DL이 크게 못 이기나** → 이 라벨의 핵심 신호(간격이 벌어지는 패턴)를 **러닝 집계 피처(직전 간격·간격비·평균 간격)가 이미 요약**하기 때문. 17-1과 같은 결론: *단일 스칼라로 요약되는 신호*에선 시퀀스 모양의 추가 이득이 작다.
- **운영 선택**: 성능이 동률이면 **지연 0.08ms·무의존성의 LogReg/GBM이 실시간에 압도적으로 유리**(DL은 수 ms + torch 의존). → **경량 ML을 실시간 스코어러로 채택**, DL은 순서 의존이 강해질 때(아래 7번) 재검토.

> demo: ![sessions](../sample_project/outputs/realtime/sessions_demo.png)
> 이탈 세션들의 실시간 확률이 세션이 진행될수록 상승해 thr=0.5를 넘는 순간 개입이 발동된다.

## 5. 이탈방지 프로토콜 — 케이던스(예측 간격)별 성능 ★

각 이탈세션을 `prob>0.5` 처음 넘는 시점에 **플래그(개입 발동)** → 세션 마지막 이벤트까지를 **리드타임**으로.

| 예측 간격 | 탐지율(recall) | 정밀도 | 리드타임 중앙 | 스코어링/세션 |
| --- | --- | --- | --- | --- |
| **이벤트 구동** | **0.63** | 0.76 | 52s | **5.2** |
| 5초 tick | 0.46 | 0.71 | 104s | 45.2 |
| 30초 tick | 0.40 | 0.72 | 126s | 8.0 |
| 60초 tick | 0.35 | 0.73 | 136s | 4.3 |
| 300초 tick | 0.12 | 0.76 | 320s | 1.4 |

**해석 (베스트 옵션 결론)**
- **이벤트 구동이 탐지율 최고(0.63)이면서 스코어링 비용은 낮음(5.2/세션)** — 정보가 도착하는 순간에만 평가하므로 짧은 세션까지 놓치지 않고, 유휴 시간엔 낭비가 없다. **5초 tick은 9배 더 스코어링하고도 recall이 더 낮다**(정보 없는 시점을 헛스코어).
- 고정 tick은 **간격이 길수록 리드타임은 늘지만 탐지율 급락**(긴 세션만 잡고 짧은 세션 놓침). 300초는 리드 320s지만 recall 0.12로 대부분 놓침.
- **따라서 베스트 = "이벤트 구동(per-event) 스코어링"을 기본으로**, 거기에 **30~60초 워치독 tick을 보조**로 더해 "마지막 이벤트 후 침묵이 자라는 구간"의 리드타임을 보강(이벤트 구동의 약점인 종료직전 늦은 플래그 보완).
- 임계값(thr)으로 recall↔정밀도↔리드타임을 운영 목표에 맞춰 조정(공격적 개입=낮은 thr, 비용 절감=높은 thr).

**권장 프로토콜 사양**
```
세션 정의      : 30분 무활동 = 종료
스코어링 트리거 : 이벤트 구동(매 이벤트, 평균 ~18s 간격) + 30s 워치독
모델          : 경량(LogReg/GBM), 단건 <0.2ms
발동 조건      : P(이탈임박) ≥ thr(기본 0.5; 운영 튜닝)
개입          : exit-intent 쿠폰 / 실시간 추천 / 재방문 푸시
종료 평가      : 마지막 이벤트 후 30분 무활동 → 이탈 확정(win-back 단계로 이관)
```

## 6. 17-0/17-1과의 관계 (시간 척도 정리)

| 리포트 | 시간 단위 | 라벨 | 개입 | 모델 |
| --- | --- | --- | --- | --- |
| 17-0/17-1 | **일(day)** | 7일 무활동 churn | 느린 리텐션(이메일/쿠폰) | DL≈GBM(+recency) |
| **17-2** | **초(event)** | 세션 무구매 이탈 임박 | 실시간 개입(팝업/푸시) | 경량 ML로 충분 |

→ 두 척도는 **상호보완**: 17-2(세션 내 실시간 방어)로 즉시 이탈을 막고, 막지 못하면 30분 timeout 후 17-0/17-1(일 단위 win-back)로 넘긴다. 하나의 파이프라인에서 **빠른 루프 + 느린 루프**로 연결.

## 7. 다음 단계
1. **실데이터 세션 라벨 검증**: REES46 `session_id`로 실제 세션-이탈(무구매 종료)을 라벨링해 합성 결과를 부분 검증(희소하지만 분포 일치 확인용).
2. **개입 효과 모델링**: 플래그→개입→복귀 확률을 넣어 "구할 수 있는 이탈"의 기대 매출 효과를 시뮬.
3. **워치독 하이브리드 정량화**: 이벤트구동+30s 워치독 조합의 recall/리드타임을 별도 측정.
4. **온라인 학습**: 스트림에서 점진 업데이트(concept drift 대응).
5. **Streamlit 연동**: `simulate_events.py`로 이 스트림을 DB에 흘려 대시보드가 실시간 게이지로 렌더(05-x 아키텍처의 빠른 루프 데모).
