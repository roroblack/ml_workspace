## 1. 액션 플랜에 넣을 최종 I/O 계약 요약

| 계약 블록 | 입력 | 처리 주체 | 출력 | 저장/노출 위치 |
| --- | --- | --- | --- | --- |
| 모델 등록 | 모델 파일, manifest, 평가 산출물 | FastAPI 백엔드 | `model_registry`, `model_evaluation` 등록 | `POST /models/submit`, MySQL |
| 실시간 이탈 예측 | 시뮬레이션 이벤트, 유저/세션 정보, active churn model | FastAPI 백엔드 | `churn_probability`, `risk_level`, `recommended_action` | `prediction_log`, `/predictions/*` |
| 세션 바운스 예측 | 첫 30분 세션 진행 피처, active bounce model | FastAPI 백엔드 | `bounce_probability`, `churn30`, 바운스 액션 | `sim_event_log`, `data/processed/session_bounce/`, `/session-bounce/*` 후보 |
| 추천/카테고리 추천 | 장바구니/조회 이벤트, 상품/카테고리 catalog, 추천 모델 artifact | FastAPI 백엔드 | 추천 상품/카테고리 top-k JSON | `recommendation`, `/recommendations/*` |
| 대시보드 시각화 | 평가 JSON/parquet, 예측 로그, 추천 로그 | FastAPI 백엔드 | chart-ready JSON | `/dashboard/*`, `/models/:id/charts/*` |
| 시뮬레이션 사이트 | 상품 클릭, 장바구니, 구매, 제거 이벤트 | 시뮬 사이트 -> 백엔드/Neon | 이벤트 로그, 실시간 예측 요청 | `/sim/event`, `/api/recommendations` |
| 리텐션 액션 | 예측 ID, 액션 타입, 메시지 | 대시보드 -> 백엔드 | 쿠폰/리마인드/추천 실행 로그 | `retention_action_log`, `POST /retention-actions` |
| 얼굴 로그인 | multipart 이미지, user_id, display_name | 대시보드 -> 백엔드 | 백엔드 임베딩, 기본 `customer` 사용자, 로그인 로그 | `face_user`, `face_login_log`, `/auth/face/check-id`, `/auth/face/login` |

핵심 경계는 하나다. **모델팀은 학습 산출물을 만들고, 백엔드는 그 산출물을 읽어서 서빙/저장/API 응답을 담당한다.** 대시보드와 시뮬레이션 사이트는 DB나 모델 파일을 직접 읽지 않고 백엔드 REST만 호출한다.

## 2. 팀별 책임 경계

| 팀/영역 | 해야 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 모델팀 | 학습 코드, 모델 파일, manifest, 평가 산출물, feature schema 제출 | 백엔드 API, DB insert, Streamlit 화면 구현 |
| 백엔드팀 | 모델 등록, 실시간 추론, 추천 조립, DB 저장, chart JSON 제공 | 모델 재학습, 대시보드 렌더링 |
| 대시보드팀 | 백엔드 API 호출, 응답 렌더링, mock/실서버 전환 | DB 직접 조회, 모델 파일 직접 로드 |
| 시뮬레이션팀 | 상품/카테고리 조회, 사용자 이벤트 전송, 추천/이탈 결과 표시 | churn 계산 직접 구현 |
| DB/데이터 담당 | MySQL schema, seed, artifact path 관리 | 대용량 parquet/model 파일을 DB에 직접 저장 |

## 3. Churn 모델 산출물 I/O 계약

### 3.1 최종 발표 모델

| 모델 | model_key | 운영 상태 |
| --- | --- | --- |
| CatBoost | `catboost` | 실시간 데모 기본 active 후보 |
| LightGBM | `lightgbm` | 모델 비교/성능 시각화 후보 |
| XGBoost | `xgboost` | 실시간/대시보드 후보 |

### 3.2 모델팀 제출 필수 파일

```text
models/churn/{model_key}/
├── model.*
├── feature_schema.json
└── model_config.json

data/processed/evaluation/churn/{model_key}/
├── model_run_manifest.json
├── eval_predictions.parquet
├── metrics_summary.json
├── cohort_summary.json
├── pr_curve.json
├── threshold_curve.json
├── lift_curve.json
├── calibration_curve.json
└── business_value.json
```

현재 백엔드 실시간 추론은 `models/preprocessors/prep_{Model}_v2.joblib` 서빙 번들을 우선 사용한다. 따라서 액션 플랜에는 아래도 운영 artifact로 명시한다.

```text
models/preprocessors/
├── prep_CatBoost_v2.joblib
├── prep_LightGBM_v2.joblib
└── prep_XGBoost_v2.joblib
```

선택/부록 산출물은 아래로 둔다. 특히 `SHAP Summary`는 26-8 기준으로 환경 이슈가 있어 필수가 아니다. 대시보드는 `shap_summary.json`이 있으면 사용하고, 없으면 `feature_importance.json` 또는 모델 네이티브 feature importance로 폴백한다.

```text
data/processed/evaluation/churn/{model_key}/
├── data_distribution.json
├── score_distribution.json
├── roc_curve.json
├── confusion_matrix.json
├── value_at_risk.json
├── feature_importance.json
└── shap_summary.json
```

### 3.3 `eval_predictions.parquet` 최소 컬럼

| 컬럼 | 용도 |
| --- | --- |
| `user_id` | 유저별 예측/추천/대시보드 연결 |
| `model_name` | 모델 비교 표시 |
| `split` | train/test/oot 구분 |
| `y_true` | 실제 이탈 라벨 |
| `y_score` | 7일 이내 이탈 확률 |
| `y_pred` | threshold 적용 결과 |
| `threshold` | 분류 기준값 |
| `cohort_flag` | cohort retention 분석 |
| `revenue` | revenue recovery 계산 |
| `top_category` | 추천/세그먼트 보강 |
| `top_brand` | 추천/세그먼트 보강 |

## 4. 추천/다음 카테고리 모델 I/O 계약

추천은 서버가 직접 조립한다. 모델팀에게 완성된 추천 서버를 요구하지 않고, 서버가 로드 가능한 학습 산출물을 요구한다.

### 4.1 제출 위치

| 작업 | 모델 위치 | 평가 산출물 위치 |
| --- | --- | --- |
| 다음 카테고리 예측 | `models/next_category/{model_key}/` | `data/processed/evaluation/next_category/{model_key}/` |
| 아이템 추천 | `models/recommendation/{model_key}/` | `data/processed/evaluation/recommendation/{model_key}/` |

### 4.2 추천 모델 제출 필수 파일

```text
models/recommendation/{model_key}/
├── model.*
├── model_config.json
├── feature_schema.json
├── sample_prediction.json
├── product_vocab.json          # 모델 출력이 product index이면 필수
└── preprocessor.joblib         # 별도 변환기를 썼으면 필수

data/processed/evaluation/recommendation/{model_key}/
├── model_run_manifest.json
├── metrics_summary.json
└── eval_predictions.parquet
```

### 4.3 다음 카테고리 제출 필수 파일

```text
models/next_category/{model_key}/
├── model.*
├── model_config.json
├── feature_schema.json
├── category_vocab.json
└── sample_prediction.json

data/processed/evaluation/next_category/{model_key}/
├── model_run_manifest.json
├── metrics_summary.json
└── eval_predictions.parquet
```

### 4.4 서버 추천 fallback 순서

| 순위 | 방식 | 필요한 입력 |
| --- | --- | --- |
| 1 | item recommendation active model | 세션 이벤트, 상품 후보, 추천 모델 |
| 2 | next category active model + category catalog | 세션 이벤트, 카테고리 vocab, 상품 catalog |
| 3 | category similarity + popularity | `category_similarity`, `product_catalog`, 이벤트 수 |
| 4 | 인기 상품 fallback | 전체 인기 상품/카테고리 seed |

### 4.5 추천 응답 JSON 스키마

시뮬레이션 사이트와 대시보드가 공통으로 기대할 수 있는 추천 응답은 top-k 카테고리와 top-k 상품을 함께 담는다. 기본 top-k는 5개를 권장한다.

```json
{
  "user_id": "u-001",
  "session_id": "s-001",
  "source": "model:item_recommendation:randomforest",
  "top_categories": [
    {
      "category_id": "cat-102",
      "category_name": "skin-care",
      "score": 0.83,
      "reason": "next_category_model"
    }
  ],
  "recommendations": [
    {
      "product_id": "3762",
      "category_id": "cat-102",
      "name": "sample product",
      "brand": "sample brand",
      "price": 12900,
      "score": 0.78,
      "reason": "same_category_popular"
    }
  ]
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `source` | Y | `model:item_recommendation:*`, `model:next_category:*`, `fallback:category_similarity` |
| `top_categories` | N | 다음 카테고리 모델 또는 fallback 결과 |
| `recommendations` | Y | 최종 상품 추천 top-k |
| `score` | Y | 모델 점수 또는 유사도/인기도 점수 |
| `reason` | Y | 추천 사유. 프론트 표시와 디버깅에 사용 |

### 4.6 추천 산출물 경로 매핑

19-3-1의 운영 목표 경로와 현재 실험 산출물 경로를 아래처럼 연결한다.

| 작업 | 현재 실험 산출물 | 운영 반영 목표 |
| --- | --- | --- |
| 다음 카테고리 | `preprocessing_project/v4-1_rec_category/output/{Model}/prep_{Model}_rec.joblib` | `models/next_category/{model_key}/model.joblib` 또는 `preprocessor.joblib` |
| 다음 카테고리 vocab | `preprocessing_project/v4-1_rec_category/output/classes_cat.json` | `models/next_category/{model_key}/category_vocab.json` |
| 아이템 추천 | `preprocessing_project/v4-2_rec_item/output/{Model}/prep_{Model}_rec.joblib` | `models/recommendation/{model_key}/model.joblib` 또는 `preprocessor.joblib` |
| 아이템 vocab | `preprocessing_project/v4-2_rec_item/output/classes_item.json` | `models/recommendation/{model_key}/product_vocab.json` |

실험 폴더는 백업/검증용이고, 서버 실시간 연동 시에는 운영 목표 경로로 복사하거나 manifest에서 해당 실험 경로를 명시한다.

## 5. 세션 바운스(churn30) I/O 계약

세션 바운스는 7일 이탈 예측과 별도 트랙이다. 목적은 사용자의 첫 30분 또는 세션 초반 행동으로 “이번 세션에서 바로 이탈할 가능성”을 판단하는 것이다.

### 5.1 현재 산출물

```text
preprocessing_project/v4-3_bounce/output/
├── train_bounce.parquet
├── test_bounce.parquet
├── meta_bounce_train.json
├── meta_bounce_test.json
├── CatBoost/prep_CatBoost_bin.joblib
├── LightGBM/prep_LightGBM_bin.joblib
└── XGBoost/prep_XGBoost_bin.joblib
```

### 5.2 운영 반영 목표

```text
data/processed/session_bounce/
├── train_bounce.parquet
├── test_bounce.parquet
├── meta_bounce_train.json
└── meta_bounce_test.json

models/session_bounce/{model_key}/
├── prep_{Model}_bin.joblib
├── feature_schema.json
└── model_config.json
```

### 5.3 입력/출력 계약

| 구분 | 계약 |
| --- | --- |
| label | `churn30` 또는 `bounce` |
| horizon | 세션 초반 30분 |
| 입력 | 세션 진행 피처, `view/cart/remove/purchase`, 카테고리/브랜드/가격 요약 |
| 출력 | `bounce_probability`, `bounce_risk_level`, `recommended_action` |
| 사용처 | 시뮬 사이트 즉시 개입, 대시보드 session-bounce 카드 |

응답 예시:

```json
{
  "session_id": "s-001",
  "user_id": "u-001",
  "task": "session_bounce",
  "horizon_minutes": 30,
  "bounce_probability": 0.81,
  "bounce_risk_level": "high",
  "recommended_action": {
    "action_type": "limited_discount",
    "trigger": "view_only_session",
    "message": "지금 보는 카테고리의 한정 할인 상품을 노출합니다."
  }
}
```

## 6. 대시보드 API I/O 계약

대시보드는 `dashboard_streamlit/`에서 구현하고, 모든 데이터는 FastAPI REST로 받는다. 개발 중에만 `dashboard_streamlit/mocks/`를 사용한다.

### 6.1 공통 호출

| 목적 | Method | Endpoint | 대시보드 사용처 |
| --- | --- | --- | --- |
| 서버 상태 확인 | GET | `/health` | 앱 시작 |
| active 모델 조회 | GET | `/models/active` | 모델별 차트 기준 |
| KPI 요약 | GET | `/dashboard/summary` | 상단 KPI 카드 |
| 유저 대시보드 | GET | `/dashboard/user/:userId` | 개인 이탈/추천 탭 |
| 최신 예측 | GET | `/predictions/latest?user_id={userId}` | 이탈 확률 카드 |
| 고위험 고객 | GET | `/predictions/top-risk` | 위험 고객 테이블 |
| 추천 조회 | GET | `/recommendations/:userId` | 추천/리텐션 탭 |
| 리텐션 기록 | POST | `/retention-actions` | 쿠폰/리마인드 실행 |

### 6.2 시각화 호출

대시보드는 15개 후보 차트를 모두 받을 수 있게 구현한다. 발표에서 우선 사용할 항목은 27번 리포트의 핵심 8개로 고정한다.

| 발표 우선 항목 | Endpoint |
| --- | --- |
| 시스템 아키텍처 | `/dashboard/charts/system-architecture` 또는 정적 구조도 |
| Cohort Retention | `/dashboard/charts/cohort-retention` |
| 모델별 베이스라인 비교 | `/dashboard/charts/baseline-comparison` |
| PR-AUC | `/models/:modelId/charts/pr-auc` |
| Threshold P/R/F1 | `/models/:modelId/charts/threshold` |
| Lift Chart | `/models/:modelId/charts/lift` |
| Calibration | `/models/:modelId/charts/calibration` |
| Revenue Recovery | `/models/:modelId/charts/revenue-recovery` |

추가 후보 15개 전체 수신 계약은 19-4 기준을 유지한다.

```text
/dashboard/charts/system-architecture
/dashboard/charts/data-distribution
/dashboard/charts/cohort-retention
/dashboard/charts/baseline-comparison
/models/:modelId/charts/train-val-loss
/models/:modelId/charts/pr-auc
/models/:modelId/charts/roc-auc
/models/:modelId/charts/score-distribution
/models/:modelId/charts/threshold
/models/:modelId/charts/confusion-matrix
/models/:modelId/charts/lift
/models/:modelId/charts/calibration
/models/:modelId/charts/shap-summary
/models/:modelId/charts/value-at-risk
/models/:modelId/charts/revenue-recovery
```

`/models/:modelId/charts/shap-summary`는 부록/선택 차트다. 해당 JSON이 없으면 `/models/:modelId/charts/feature-importance` 또는 동일 구조의 `feature_importance.json`을 사용한다.

## 7. 시뮬레이션 사이트 I/O 계약

### 7.1 시뮬레이션 seed 입력

| 파일 | 용도 |
| --- | --- |
| `simulation_site/neon/seed/products.csv` | 상품 목록 |
| `simulation_site/neon/seed/categories.csv` | 카테고리 목록 |
| `simulation_site/neon/seed/brands.csv` | 브랜드 목록 |
| `simulation_site/neon/seed/category_similarity.csv` | 유사 카테고리 추천 fallback |

### 7.2 실시간 이벤트 입력

| 필드 | 설명 |
| --- | --- |
| `user_id` | 사용자 식별자 |
| `session_id` | 세션 식별자 |
| `event_type` | `view`, `cart`, `remove_from_cart`, `purchase` |
| `product_id` | 상품 ID |
| `category_id` | 카테고리 ID |
| `brand` | 브랜드 |
| `price` | 상품 가격 |
| `quantity` | 수량 |
| `event_at` | 이벤트 시각 |

### 7.3 실시간 흐름

```text
GET /sim/products
GET /sim/categories
POST /sim/event
  -> event 저장
  -> feature 생성
  -> active churn model 추론
  -> recommendation 생성
  -> prediction_log/recommendation 저장
  -> churn_probability, risk_level, recommendations 반환
```

### 7.4 서버-시뮬 사이트 연결 방식

현재 실제 코드 기준으로는 시뮬 사이트가 FastAPI 백엔드 주소를 알고 호출하는 direct 연결이 기본이다.

| 구분 | 현재 구현 | 액션 플랜 표현 |
| --- | --- | --- |
| 백엔드 주소 | 시뮬 사이트 `VITE_FASTAPI_URL`, 기본 `http://localhost:8090` | 시뮬 사이트는 백엔드 API 주소를 환경변수로 가진다 |
| 인증 키 | 백엔드 `/sim/*`는 `X-API-Key`, `/api/*` 외부 어댑터는 raw JSON 계약 | 운영형은 API key/HMAC, 데모형은 raw adapter |
| 연결 확인 | 시뮬 사이트가 `/health` 도달 여부 확인 | 시작 시 backend ping/sync |
| 이벤트 전달 | `POST /api/events` 또는 `POST /sim/event` | 시뮬 사이트가 이벤트를 백엔드로 push |
| 예측 요청 | `POST /api/churn/predict` 또는 `/sim/event` 즉시 재점수 | 백엔드가 active model로 churn 계산 |
| 추천 요청 | `POST /api/recommendations` | 백엔드가 추천 상품/카테고리 반환 |

`서로 임베딩된 해시키값`이라는 표현은 실제 구현에서는 아래처럼 정리하는 것이 안전하다.

```text
SIM_SHARED_SECRET 또는 API_KEY
-> 시뮬 사이트 요청 Header: X-API-Key 또는 X-Signature
-> 백엔드 검증
-> 연결 성립
```

데모에서는 현재 구조처럼 `VITE_FASTAPI_URL`로 백엔드 주소를 알고, 백엔드 CORS를 열어 direct 호출하는 방식이 가장 빠르다. 운영형으로 설명할 때는 `X-API-Key` 또는 HMAC signature를 추가해 서버-시뮬 사이트 간 신뢰 관계를 만든다고 설명한다.

### 7.5 Neon과 운영 MySQL 역할 분리

시뮬 사이트는 Neon DB를 별도로 가질 수 있다. Neon에는 상품/카탈로그/브랜드/가격 seed와 시뮬 이벤트 원천 로그를 둔다. 운영 백엔드 MySQL에는 모델 등록, 예측 결과, 추천 결과, 리텐션 액션 결과를 둔다.

| 저장소 | 저장 대상 | 현재 프로젝트 위치 |
| --- | --- | --- |
| Neon/Postgres | 상품, 카테고리, 브랜드, 가격, 시뮬 이벤트 원천 | `simulation_site/neon/seed/*.csv`, `schema_neon.sql` |
| MySQL | 모델 레지스트리, 예측 로그, 추천 로그, 리텐션 액션, 얼굴 로그인 | `backend/db/schema_mysql.sql` |
| 파일 시스템 | 모델, 전처리 번들, 평가 parquet/json | `models/`, `data/processed/evaluation/` |

현재 백엔드 DB에는 `sim_event_log`가 있어 로컬/데모에서는 이벤트 로그를 MySQL에도 저장할 수 있다. Neon을 원천으로 쓰는 경우에도 백엔드는 필요한 이벤트를 받아 `sim_event_log` 또는 메모리 세션에 반영한 뒤 churn 계산을 수행한다.

### 7.6 실시간 액션 반환 계약

백엔드는 churn 결과만 반환하지 않고, 현재 이벤트 맥락에 맞는 retention action도 함께 반환한다. 이 값은 대시보드 표시와 시뮬 사이트 UI 개입에 모두 사용할 수 있다.

| 상황 | 조건 예시 | 서버 반환 액션 | 시뮬 사이트 처리 | 기대 효과 |
| --- | --- | --- | --- | --- |
| 장기 미접속 후 접속 | `profile=lapsing`, `recency_days` 높음 | `sns_link`, `welcome_back` | SNS 연동/혜택 페이지 노출 | view 이벤트 증가, 이탈 위험 완화 |
| 장바구니 담고 미구매 | `cart > 0`, `purchase = 0` | `discount_coupon`, `related_products` | 할인 쿠폰, 연관상품 추천 | 구매 전환 유도 |
| 조회만 반복 | `view` 증가, `cart/purchase` 없음 | `limited_discount`, `popular_items` | 할인/인기상품 노출 | 탐색 피로 완화 |
| 장바구니 제거 | `remove_from_cart` 발생 | `alternative_items` | 대체상품 추천 | 이탈 전환 방지 |
| 구매 발생 | `purchase > 0` | `thank_you`, `cross_sell` | 감사 메시지, 연관상품 | 재방문/추가 구매 유도 |

권장 응답 필드는 아래처럼 잡는다.

```json
{
  "session_id": "s-001",
  "user_id": "u-001",
  "churn_probability": 0.72,
  "risk_level": "high",
  "recommended_action": {
    "action_type": "discount_coupon",
    "message": "장바구니 상품 10% 할인 쿠폰을 제공합니다.",
    "trigger": "cart_without_purchase",
    "ui_target": "cart_modal"
  },
  "recommendations": []
}
```

현재 코드의 `recommended_action`은 문자열 중심이므로, 액션 플랜에서는 구조화 JSON으로 확장하는 것을 목표로 둔다. DB 저장은 기존 `retention_action_log.action_type`, `action_message`, `status`로 받을 수 있다.

## 10. 액션 플랜 페이지에 들어갈 카드 문구

### 10.1 모델 산출물 계약

모델팀은 `models/churn/{model_key}/`에 모델/스키마/설정 파일을 두고, `data/processed/evaluation/churn/{model_key}/`에 평가 산출물을 둔다. 백엔드는 manifest를 검증해 MySQL에 모델과 평가 결과를 등록한다.

### 10.2 실시간 예측 계약

시뮬레이션 사이트는 사용자 이벤트를 백엔드로 보내고, 백엔드는 active churn model로 7일 이내 이탈 확률을 계산해 `prediction_log`에 저장한다.

### 10.3 세션 바운스 계약

세션 초반 30분 행동은 별도 `session_bounce` 트랙으로 처리한다. 백엔드는 `prep_*_bin.joblib` 바운스 모델로 `bounce_probability`를 계산하고, 즉시 할인/추천/리텐션 액션으로 연결한다.

### 10.4 추천 계약

추천은 서버 책임이다. 모델팀은 추천 모델 artifact와 vocab/schema/sample을 제공하고, 백엔드는 세션 이벤트를 feature로 바꿔 top-k 상품/카테고리 추천을 생성한다. 추천 모델이 없으면 카테고리 유사도와 인기 상품으로 fallback한다.

### 10.5 대시보드 계약

대시보드는 DB와 모델 파일을 직접 읽지 않는다. `GET /dashboard/*`, `GET /predictions/*`, `GET /recommendations/*`, `GET /models/:id/charts/*` 응답만 받아 Streamlit에서 렌더링한다.

### 10.6 DB 저장 계약

대용량 parquet/npz/model 파일은 파일로 보관하고, MySQL에는 경로와 요약 JSON만 저장한다. 운영 로그는 `prediction_log`, `recommendation`, `retention_action_log`, `face_login_log`에 남긴다.

## 11. 최종 판정

19-2부터 19-6까지의 결정과 27번 핵심8 시각화 결정은 아래처럼 정리하면 충돌하지 않는다.

1. 백엔드는 FastAPI/Python으로 모델 서빙, DB 저장, chart-ready JSON 제공을 담당한다.
2. 모델팀은 최종 3개 churn 모델인 CatBoost, LightGBM, XGBoost 산출물을 19-3 형식으로 제출한다.
3. 추천/다음 카테고리는 19-3-1 형식으로 모델 artifact만 받고, 추천 알고리즘 조립과 fallback은 백엔드가 담당한다.
4. 대시보드는 19-4/19-5 기준으로 통합 화면 하나에서 API 응답을 렌더링한다.
5. 실시간 시뮬레이션은 19-6 기준으로 CatBoost active 모델과 `prep_*_v2.joblib` 서빙 번들을 우선 사용하면 데모가 가능하다.
6. 발표 우선 시각화는 27번 핵심8로 고정하고, SHAP은 부록/선택으로 두며 feature importance 폴백을 기본으로 한다.
7. 세션 바운스는 `churn30` 별도 트랙으로 추가하고, `v4-3_bounce` 산출물을 운영 경로에 매핑한다.
