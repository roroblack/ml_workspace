# 17-3-6. 카테고리 추천에서 아이템 추천으로 전환 정리

작성일: 2026-06-22

목적: 17-3-5/17-4-0에서 수행한 "다음 카테고리 예측"과, 현재 운영/시뮬레이션 사이트에서 쓰려는 "상품 아이템 추천"의 차이를 명확히 정리한다.

---

## 1. 기존 17-3-5의 과제 정의

17-3-5는 아이템 추천 모델이 아니라 **다음 카테고리 예측 모델**이었다.

```text
입력 X:
  직전 L=10개 이벤트
  - X_num: is_view, is_cart, is_remove, is_purchase, gap_log, price_log
  - X_cat: 직전 10개 category_id index

정답 y:
  다음 이벤트의 category_id index
  - 462개 category + unknown 0
```

즉 `y`는 `product_id`가 아니라 **다음 이벤트의 category_id**였다.

---

## 2. 17-3-5 결과 요약

| 모델 | Top-1 | Hit@10 | MRR@10 | 해석 |
| --- | ---: | ---: | ---: | --- |
| Popularity | 0.0650 | 0.3310 | 0.1310 | 단순 인기 카테고리 기준 |
| Last-category | **0.5772** | 0.7906 | **0.6482** | 직전 카테고리가 매우 강함 |
| LSTM | 0.5656 | 0.7864 | 0.6372 | DL이 휴리스틱을 크게 넘지 못함 |
| GRU | 0.5671 | 0.7899 | 0.6406 | 운영 후보로 선정 |
| Transformer | 0.5677 | 0.7953 | 0.6432 | Hit@10은 강하지만 비용 큼 |
| SASRec | 0.5682 | **0.7961** | 0.6436 | 기술 최고치이나 차이가 작음 |

핵심 해석:

- 화장품 세션은 같은 카테고리를 연속 탐색하는 경향이 강하다.
- 그래서 "다음 카테고리 ≈ 방금 본 카테고리" 휴리스틱이 매우 강했다.
- 카테고리 462개는 상품 5만 개보다 훨씬 낮은 차원이므로 DL/SASRec의 장점이 크게 드러나지 않았다.

---

## 3. 현재 운영 추천의 과제 정의

현재 시뮬레이션/대시보드 추천은 다음 구조에 가깝다.

```text
입력:
  product_id 또는 category_id 또는 user top_category

출력:
  추천 product_id 목록 top_k

사용 산출물:
  data/processed/recommendation/product_catalog.parquet
  data/processed/recommendation/category_similar.parquet
  data/processed/recommendation/category_catalog.parquet
```

현재 방식은 supervised ML/DL 모델이라기보다 **룰 + 통계 기반 추천**이다.

```text
장바구니/현재 상품 product_id
  -> product_catalog에서 category_id 조회
  -> 같은 category 또는 category_similar의 유사 category 조회
  -> product_catalog에서 n_events 높은 상품 정렬
  -> 이미 장바구니에 있는 상품 제외
  -> top_k product_id 반환
```

따라서 현재 운영 추천에는 17-3-5 같은 의미의 `y`가 없다.

---

## 4. 아이템 추천으로 학습하려면 y가 어떻게 바뀌나

상품목록 기반 학습 모델로 바꾸면 과제 정의는 아래처럼 바뀐다.

```text
입력 X:
  유저/세션의 과거 이벤트 시퀀스
  - 최근 product_id sequence
  - 최근 category_id sequence
  - event_type sequence
  - price/gap/count 피처
  - 장바구니/구매/조회 누적 피처

정답 y:
  다음에 조회/장바구니/구매한 product_id
```

즉 `y`가 `category_id`에서 **product_id**로 바뀐다.

---

## 5. 데이터셋 구성 차이

| 구분 | 17-3-5/17-4-0 | 현재 운영 추천 | v5 신규 예정 |
| --- | --- | --- | --- |
| 목적 | 다음 카테고리 예측 | 카탈로그 기반 상품 추천 | 다음 상품/후보 상품 예측 |
| 데이터 단위 | 세션 window | 카탈로그/유사도 사전 | 세션 window 또는 유저×상품 후보 |
| 입력 | `X_num(10,6)`, `X_cat(10)` | product/category catalog | 최근 상품·카테고리·행동 sequence + tabular |
| 정답 y | 다음 `category_id` | 없음, 무라벨 추천 | 다음 `product_id` |
| 출력 | category rank | product_id top_k | product_id top_k |
| 성능지표 | Top-1, Hit@10, MRR@10 | 오프라인 지표 없음 | Top-1, Hit@10, MRR@10 |

---

## 6. 왜 상품 레벨이 더 어려운가

상품 레벨은 카테고리 레벨보다 훨씬 어렵다.

| 항목 | 카테고리 예측 | 상품 예측 |
| --- | --- | --- |
| 클래스 수 | 약 462개 | 약 54,571개 |
| 반복성 | 같은 카테고리 반복이 많음 | 같은 상품 반복은 상대적으로 적음 |
| 콜드스타트 | 낮음 | 높음 |
| 학습비용 | 낮음 | 높음 |
| 추천 활용도 | 카테고리 추천 | 실제 상품 추천 |

따라서 상품 레벨은 처음부터 54,571개 전체 softmax로 가기보다 다음 단계가 현실적이다.

1. top-N 인기 상품으로 빠른 벤치마크를 수행한다.
2. 성능과 병목을 확인한다.
3. 이후 전체 상품은 candidate retrieval + reranking 구조로 확장한다.

---

## 7. 결론

17-3-5는 **다음 카테고리 예측 실험**이었다. 현재 운영 추천은 **카테고리/상품 카탈로그 기반의 룰+통계 추천**이다.

상품목록으로 학습을 진행하려면 새 v5에서는 `y=다음 product_id`로 과제를 다시 정의해야 한다. 이 경우 클래스 수가 5만 개 이상으로 커지므로, 1차는 top-N 상품 후보군을 대상으로 Top-1/Hit@10/MRR@10을 비교하고, 2차로 전체 상품 후보 검색 구조로 확장하는 것이 맞다.
