## 1. 핵심 정정

19-2 기준으로 **서빙은 백엔드 책임**이다.

모델팀에게 추천 알고리즘 전체나 서버용 API 구현을 요구하지 않는다. 모델팀은 학습된 모델 파일과 학습 산출물을 제출하고, 백엔드가 그 파일을 로드해서 실시간 이벤트를 feature로 바꾸고 추천 알고리즘을 조립한다.

정확한 책임 분리는 아래다.

| 구분 | 책임 |
| --- | --- |
| 모델팀 | 학습 코드, 모델 artifact, 학습 입력/출력 명세, vocab/id mapping, 평가 산출물 |
| 백엔드팀 | 모델 로딩, 실시간 feature 생성, 후보 상품 생성, 추천 알고리즘, API 응답, DB 저장 |
| 대시보드/시뮬 | 백엔드 API 호출, 추천 결과 표시 |

따라서 모델팀에게 "모델 자체만" 받는 것도 부족하지만, "서빙 전체를 해달라"고 요구하는 것도 아니다.

올바른 요구는 아래다.

```text
모델팀:
  서버가 직접 서빙할 수 있도록 학습 산출물 패키지를 제출한다.

백엔드팀:
  그 산출물을 로드해서 실시간 추천 알고리즘과 API를 구현한다.
```

## 2. 19-2 기준 추천/다음 카테고리 위치

19-2는 추천과 다음 카테고리를 churn의 부산물이 아니라 별도 태스크로 분리한다.


즉 운영 경로는 아래처럼 잡는다.

| 태스크 | 데이터 | 모델 | 평가 |
| --- | --- | --- | --- |
| 다음 카테고리 | `data/processed/next_category/` | `models/next_category/{model_key}/` | `data/processed/evaluation/next_category/{model_key}/` |
| 아이템 추천 | `data/processed/recommendation/` | `models/recommendation/{model_key}/` | `data/processed/evaluation/recommendation/{model_key}/` |

## 3. 현재 서버 추천 구조

현재 서버는 이미 추천 API를 갖고 있다.

### 3.1 대시보드 추천

```text
GET /recommendations/{user_id}
```

현재 흐름:

```text
eval_predictions.parquet 또는 유저 관심 정보의 top_category
-> data/processed/recommendation/category_similar.parquet
-> 유사 카테고리 반환
```

### 3.2 시뮬레이션 사이트 추천

```text
POST /api/recommendations
```

현재 요청:

```json
{
  "session_id": "s1",
  "user_id": "u1",
  "current_product_id": "3762",
  "category_id": "1487580011677352062",
  "brand": "some_brand"
}
```

현재 흐름:

```text
category_id
-> simulation_site/neon/seed/category_similarity.csv
-> simulation_site/neon/seed/products.csv
-> 유사 카테고리의 인기 상품 반환
```

이 구조는 유지한다. 추천 모델이 들어와도 API 계약은 최대한 유지하고, 내부 usecase만 확장한다.

## 4. 서버가 구현할 추천 알고리즘

서버 추천 알고리즘은 아래 2단계가 기본이다.

```text
1. Candidate generation
   - current_product_id의 category 조회
   - 같은 category 상품 후보
   - category_similarity 기반 유사 category 상품 후보
   - global popularity 후보
   - 최근 세션 product/category 후보

2. Ranking / Reranking
   - 모델이 있으면 후보 상품을 점수화
   - 모델이 없으면 n_events, cosine, same_category, same_brand 기반 rule score
   - top_k product_id 반환
```

서버가 이 알고리즘을 책임진다.

모델팀 모델은 2단계의 reranker 또는 direct top-k predictor로 쓰인다.

## 5. 모델팀에게 요구할 공통 산출물

모델팀에게 요구할 것은 "서버가 읽을 수 있는 학습 산출물"이다.

공통 필수:

```text
model.*
model_config.json
feature_schema.json
model_run_manifest.json
metrics_summary.json
eval_predictions.parquet
sample_prediction.json
```

조건부 필수:

```text
vocab.json              # 모델 출력이 index이면 필수
preprocessor.joblib     # 모델 학습 시 별도 변환기를 썼으면 필수
training_history.json   # DL/RNN/Transformer면 권장
```

중요:

- `feature_schema.json`은 서버가 실시간 이벤트를 어떻게 feature로 바꿔야 하는지 맞추기 위한 문서다.
- `vocab.json`은 모델 출력 index를 실제 `category_id` 또는 `product_id`로 복원하기 위한 파일이다.
- `sample_prediction.json`은 서버 구현자가 모델 로딩 결과를 검증하는 기준 샘플이다.

### 7.2 제출 위치


## 8. 서버 구현 형식

19-2 기준으로 서버에 추가할 파일은 아래다.

```text
backend/app/interfaces/http/recommendations_router.py
backend/app/application/create_recommendation_usecase.py
backend/app/domain/recommendation.py
backend/app/infrastructure/files/recommendation_artifact_store.py
backend/app/infrastructure/model_inference/recommendation_model_loader.py
```

이미 존재하는 현재 파일을 확장해도 된다.

```text
backend/app/interfaces/http/sim_external_router.py
backend/app/interfaces/http/sim_router.py
backend/app/application/sim_usecase.py
backend/app/infrastructure/files/catalog_store.py
```

### 8.1 추천 usecase 내부 흐름

```text
request
-> session/user context 생성
-> candidate generation
-> active recommendation model 조회
-> model_inference adapter 호출
-> top_k product/category 조립
-> recommendation 테이블 저장
-> API 응답
```

### 8.2 fallback 규칙

추천 모델이 없거나 로드 실패하면 서버는 기존 카탈로그 추천으로 fallback한다.

```text
1순위: item_recommendation active model
2순위: next_category active model + category catalog
3순위: category_similarity + product popularity rule
```

이 fallback은 서버 domain/application 계층에서 구현한다.

## 12. 지금 프로젝트 기준 추천 우선순위

17-5-4 기준 v5 fast benchmark에서 추천 top10 기준 최고는 RandomForest다.

```text
RandomForest Hit@10 = 0.768595
ExtraTrees   Hit@10 = 0.752066, Top-1/MRR 최고
```

따라서 서버 실험 우선순위:

1. 기존 카탈로그 fallback 유지
2. `models/recommendation/randomforest/`를 item recommendation active 후보로 연결
3. `models/recommendation/extratrees/`를 랭킹 품질 비교 후보로 연결
4. LightGBM/XGBoost/CatBoost는 후보 reranker 확장 실험으로 보류
5. 다음 카테고리 GRU/SASRec 계열은 category 추천용 별도 active 후보로 연결

## 13. 결론

사용자 지적대로, 19-2 기준에서는 **추천 서빙과 추천 알고리즘은 서버가 담당하는 것이 맞다**.

정리하면:

```text
모델팀:
  학습된 모델 파일과 학습 산출물 제출

서버팀:
  실시간 이벤트 -> feature 변환
  후보 상품 생성
  모델 로딩
  top_k 추천 계산
  recommendation DB 저장
  API 응답
```

따라서 모델팀에게 요구할 것은 "완성된 추천 서버"가 아니라, **서버가 직접 서빙할 수 있는 모델 산출물 형식**이다.

최소 요구:

```text
model.*
model_config.json
feature_schema.json
vocab.json 또는 product/category id 복원 정보
sample_prediction.json
model_run_manifest.json
metrics_summary.json
eval_predictions.parquet
```

이 기준으로 받아야 백엔드가 19-2 설계대로 `model_inference` adapter에서 직접 실시간 추천 연산을 수행할 수 있다.
