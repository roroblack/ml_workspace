# 프로젝트 규칙 (RULES)

> 이 문서는 `ml_unified_lab` 작업 시 **사람과 AI가 함께 지켜야 하는 규칙**을 정의한다.
> 작성 시작: 2026-06-14. 규칙이 바뀌면 이 파일과 [HISTORY.md](HISTORY.md)를 함께 갱신한다.

---

## 0. 이 프로젝트의 목적

이 프로젝트의 **가장 큰 목적은 "복습"** 이다. 그동안 진행한 ML/DL 실습을 하나의 틀에서
다시 돌려 보고, 코드를 읽고 고쳐 보고, 하이퍼파라미터를 바꿔 보며 학습 효과를 얻는 것이
최우선 가치다. 따라서 모든 기능 결정은 "이게 복습에 도움이 되는가?"를 기준으로 판단한다.

## 1. 할루시네이션 방지 규칙 (최우선)

AI 어시스턴트는 다음을 **반드시** 지킨다.

1. **추측 금지 · 확인 우선.** 파일명·함수·파라미터·라이브러리 버전·수치를 말하기 전에
   실제 파일을 읽거나 명령으로 검증한다. 기억이나 일반 지식으로 단정하지 않는다.
2. **검증된 사실만 보고.** "동작한다"는 실제로 실행해 확인했을 때만 말한다.
   실행하지 않았으면 "아직 검증 안 함"이라고 명시한다.
3. **출처를 남긴다.** 수치·결과를 인용할 때는 어느 실행(run 폴더)·어느 파일에서 나온
   값인지 밝힌다. (예: `runs/.../metrics.json` 기준)
4. **모르면 모른다고 한다.** 불확실하면 단정하지 말고 한계를 드러낸 뒤 확인 방법을 제안한다.
5. **과장 금지.** 테스트가 실패하면 출력과 함께 실패라고 말한다. 건너뛴 단계는 건너뛰었다고 말한다.
6. **기존 코드를 먼저 읽는다.** 수정·삭제 전에 대상 파일을 직접 읽어 설명과 실제가 일치하는지
   확인한다. 내가 만들지 않은 것을 덮어쓰기 전에 반드시 점검한다.

## 2. AI 하네스(harness) 작업 기법

작업은 다음 절차(하네스)를 따른다. 큰 작업일수록 엄격히 적용한다.

1. **계획 → 분해.** 요청을 작은 작업으로 쪼개고 TODO로 추적한다(한 번에 하나만 진행).
2. **사실 수집(Ground).** 코드를 읽고, 데이터를 확인하고, 라이브러리 설치 여부를 점검한 뒤 착수.
3. **작게 변경 → 즉시 검증.** 한 조각을 바꾸면 바로 실행/테스트로 확인하고 다음으로 넘어간다.
4. **적대적 검증(Adversarial check).** "이 조합이 깨지지 않나? 빈 입력은? 없는 의존성은?"을
   스스로 반증하려 시도한 뒤 통과해야 완료로 본다.
5. **결과 보고.** 무엇을 했고, 무엇을 검증했고, 무엇이 남았는지 사실대로 보고한다.
6. **기록.** 의미 있는 변경은 [HISTORY.md](HISTORY.md)에 날짜·시간과 함께 남긴다.

## 3. 하드코딩 · 폴백(fallback) 규칙

> 핵심: **하드코딩과 폴백은 가능하면 하지 않는다. 해야 한다면 반드시 사용자 허락을 먼저 받고,
> 리포트로 남긴다.**

- **하드코딩 금지(원칙).** 경로·임계값·하이퍼파라미터 등은 설정(YAML)·레지스트리·인자로
  외부화한다. 코드에 값을 박아야만 하는 상황이면 **먼저 사용자에게 묻고 승인받은 뒤** 진행하며,
  그 사유를 `reports/`에 리포트로 남긴다.
- **폴백 금지(원칙).** "안 되면 조용히 다른 걸로 대체"하는 동작은 만들지 않는다.
  불가피한 폴백(예: optuna 미설치 시 random search)은 **(1) 사용자 승인, (2) 리포트 기록,
  (3) 실행 시 화면/로그에 폴백이 일어났음을 명시**라는 3가지를 모두 충족할 때만 둔다.
- **조용한 축소 금지.** top-N 제한, 샘플링, 재시도 생략 등으로 범위를 줄였다면 로그로 분명히 알린다.
  (예: 비전 데이터 `max_train_samples` 서브샘플링은 config에 노출하고 GUI/로그에 표시한다.)

## 4. GUI 작업 규칙

- **꼭 필요한 부분만 작업한다.** 요청과 무관한 UI를 임의로 바꾸지 않는다.
- **기존 UI 수정은 사용자의 요청이 있을 때만.** 사용자가 고치라고 한 부분만 고친다.
- **불가피하게 기존 부분을 수정해야 하면** 먼저 `reports/`에 변경 사유·범위 리포트를 작성하고,
  그 내용을 사용자에게 보고한 뒤 진행한다.
- GUI는 백엔드(`src/`, `run_experiment.py`)를 호출만 한다. 학습/평가 로직을 GUI에 중복 구현하지 않는다.

## 5. 리포트 규칙

- **모든 리포트 파일은 [`reports/`](reports/) 폴더에 저장한다.**
  (이 폴더는 자동 생성 인벤토리 CSV와, 사람이 작성한 가이드/리포트 md를 함께 보관한다.)
- 리포트가 필요한 경우: 기능 추천, Colab 셋업 가이드, 하드코딩/폴백 승인 요청,
  기존 GUI 수정 사유, 설계 결정(scope 변경) 등.
- 파일명은 내용을 알 수 있게 짓는다. (예: `colab_setup_guide.md`, `review_feature_recommendations.md`)

## 6. 기록(History) 규칙

- 의미 있는 작업/결정은 [HISTORY.md](HISTORY.md)에 남긴다.
- **각 항목에는 날짜와 시간을 `YYYY-MM-DD HH:MM` 형식으로 정확히 기입한다.**
  상대 표현("어제", "방금") 대신 절대 시각을 쓴다. 시각은 `datetime.now()`로 확인한 값을 쓴다.

## 7. 코드 스타일 / 구조 규칙

- 데이터셋·모델·탐색은 **레지스트리(YAML) + 팩토리** 패턴으로 추가한다. 새 항목은 코드 수정
  최소화로 등록되게 한다.
- 새 의존성은 `requirements.txt`에 반영하고, 미설치 시 **명확한 안내 메시지**로 실패한다(조용히 죽지 않음).
- 한글 주석/로그를 사용한다. Windows 콘솔에서 깨지면 `$env:PYTHONUTF8=1` 안내.
